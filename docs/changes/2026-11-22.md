## 页面 Schema 迁出脚本：任务 / 作业 / 审计改由服务端产出（第二批）

**口径修正**：上一批把「布局」一律理解为「静态资产 JSON」，方向偏了。真正的判据是**布局是否随请求上下文变化**——不随变的进资产（镜像/网络/卷），随变的（权限、页签、记录状态）由 `crates/web` 的 UI 端点产出 JSON。这里的「内核」只指核心调用层（命令与领域服务），与服务端出不出 UI JSON 无关；站点页由服务端产 JSON 本来就是正当形态。

## 第三批复审：一个真 bug、两处漏注册、一处重复定义

迁移完成后按「断言是否真成立 + 产出端是否真被用上」重审了一遍，改了四处：

### 1. 作业日志页此前必然报错（功能缺陷）

壳脚本 `loadJobLogs` 请求的是 `{prefix}/jobs/{id}/logs?after=N`，而该路径只有 `/{p}/jobs/{id}/logs/stream`（SSE）是独立路由，普通路径由壳页接管返回 HTML。`fetchRawJson` 对 HTML 做 `JSON.parse` 必然抛错，页面从未真正可用。

改法：新增 `GET /ui/v1/jobs/{id}/logs?with_schema=true`（`jobs.rs::job_logs`，`JOB_LOGS` 鉴权）。服务端按 `after` 游标最多聚合 10 页（每页 `LOG_PAGE = 500`），合成 `HH:MM:SS [stream] line` 后交 `jobs_page::job_logs_schema` 出页面；`truncated` 时在计数行提示可刷新继续。脚本删掉 `loadJobLogs` 与 `jobLogsSchema`（97 行），`job-logs` 分支改为 `fetchServerSchema('/jobs/{id}/logs?with_schema=true')`。

### 2. 服务端下发的弹窗从未进注册表

`prepareServerSchema` → `registerServerDialog` 读 `button.action.props.body`，但 budding 1.8.3 起 dialog 的插槽在动作顶层 `content.body`（写 `props.body` 会整页 CompileError）。结果 `body` 恒为空、函数提前返回：服务端产出的弹窗（`_file-row.json` 的 6 个）全部未注册，提交失败时 `dialogError` 拿不到定义，只能退化成一闪而过的 toast。改为读 `action.content.body` 后 6/6 可注册。

同时补上「解压」弹窗 `skiffFileExtract` 缺失的 `props.dialog` —— 另外 5 个弹窗都带，只有它漏了，失败时无法回到弹窗。

### 3. 站点新建字段抄了两份

`site_page::site_create_fields` 的注释写着「列表弹窗与 `/sites/new` 深链页共用同一份定义」，但 `sites_extra_page::site_new_schema` 另写了一份相同的 7 个字段（已是两份不同实现：`kit::select` 会多写 `defaultValue`）。改为 `pub(super) fn site_create_fields` 并让深链页直接调用，注释与实现一致。

### 4. 四条断言锁的形态已经变了

- `visibleOn: '${item.can_extract}'` → 读 `_file-row.json` 的 `"visibleOn": "${item.can_extract}"`。
- 容器新建的 `skiffDockerWrite` 与 Docker 设置的 `skiffDockerSettingsWrite` → 分别读 `docker-container-new.json` 与 `settings_page.rs`（后者顺带钉住 `/settings/docker`）。
- Web 启停按钮：原断言钉 `if container_state == "running" { "stop" } else { "start" }` 单行，而实现里同一个判断被重复比较了四次且被 rustfmt 拆成块。改为先 `let running = container_state == "running";` 再单行三元，断言随之改为 `if running { "stop" } else { "start" }`。

### 验证方式

`node --check budding-boot.js` 干净；`cargo check/clippy -p skiff-web --all-targets -- -D warnings`、`cargo fmt --all --check` 通过。另做了三项静态核对（脚本）：`main_flow.rs` 的 17 个 `budding_boot_*` 测试共 133 条正向 + 22 条负向字面断言全部成立；服务端与资产引用的 59 个 `skiff*` 动作全部在脚本注册表内；服务端产出的节点/动作 `type` 与 budding `catalog.json` 白名单一致。用例结果仍以 CI 为准。

## 第五批：路由表与页面取数地址移到服务端

路由是菜单的投影，菜单树本来就由内核算（`skiff_app::menu::build`）。壳脚本另抄一份
「菜单键 → 路径 → 页面来源」的映射，等于把同一份事实写两遍：改一个菜单项要同时改内核
与脚本，而脚本那份无法在 CI 里验证，只能靠人工点。这一批把它整体收回服务端，脚本
3966 → **3444 行**。

### 1. 新增两个端点（`handlers/ui/routes.rs`）

- `GET /ui/v1/routes`：菜单树 → budding `routes` 数组。路径、标题、图标（`MENU_ICONS`
  也搬来了）、`hidden`、`meta.order` / `meta.activeMenu`、页面来源都在服务端算好；
  另外下发 `plugins[]`（`plugin_id` / `default_view` / `views`）给三级菜单用。
- `GET /ui/v1/page?path=&search=`：回答「当前地址的页面结构去哪取」。`?tab=` 归一、
  `?path=` 透传、`?filter=error`、`?q=`、`?part=`/`?tail=` 默认值、`?refresh=1`、
  `?cursor=` 这些原先散落在 `pageSchema` 的 if/else 里，现在收进纯函数
  `page_source(prefix, path, search)`。
- 路径段**先解码再回填**，所以调用方传 `%2E` 还是 `.` 都得到同一个端点地址，不会二次编码。
- 入口前缀归一为绝对形式（`mount_prefix`）：配置里存的 `entry_prefix` 不带前导斜杠
  （挂载时才补），路由 path 与资产 URL 直接拼会得到 `p/sites/list`，与浏览器地址栏的
  `/p/sites/list` 对不上——单测传 `/p` 掩盖了这一点，靠 `mount_prefix` 的归一化单测钉住。
- 13 条单测钉住映射与编码（列表/详情/子视图/日志/Web 视图白名单/遗留 JSON 端点/未知
  路径/前缀归一）。

### 2. 壳脚本只剩两行分派

`loadJson(url)` 现在是：`skiff:page` → 问 `/page`；`skiff:<special>` → 壳体处理；

`MENU_ICONS` / `withIcon` / `pageAsset` / `pluginViewHref` / `pageSchema`（约 530 行）。

## 第六批：写请求动作名更正（ajax → request）
