## C12 收口复查补漏：测试回归 + 过时注释/文档

**背景**：2026-11-23 完成 C12（两套文件处理器并存 → 单一路径 `/ui/v1/files/*`）后重新核查，发现 clippy 不跑测试导致漏了一处真实回归，以及多处注释/文档未同步到「壳页不鉴权、数据层判定」的新行为。本次只做补漏，不改行为。

### 1. 修复真实测试回归（`main_flow.rs`）

`shell_fallback_covers_method_not_allowed_paths` 断言 `POST /p/files` 必须 405。C12 删除遗留 `handlers::files::page` 后，`/p/files` 不再有任何显式路由注册，完全靠 SPA `fallback` 承接；fallback 对非 GET 直接返 404，因此该断言实际会失败（clippy 不执行测试未暴露）。

- 改用真正「只注册了 GET」的 `/p/login`（`lib.rs` 注册了 `GET /{p}/login`）作 405 用例，测试意图不变：验证 `method_not_allowed_fallback` 接线——路径存在但方法不匹配时写请求保持 405、不被当成壳页回落。

### 2. 补测试覆盖（C12 行为变更此前无锁定）

`files_routes_are_forbidden_in_docker_restricted_form` 原只断言 `/ui/v1/files*` 数据端点 403、`/ui/v1/menu` 200，补两条：
- **菜单入口隐藏**：受限形态 `/ui/v1/menu` 下发的 href 中不含 `/p/files*`（锁定 `menu.rs` 按 `form != DockerRestricted` 过滤的逻辑，原测试 `restricted_form_hides_and_rejects_files_management` 已被删且无替代）。
- **壳页不挂门禁**：受限形态下 `GET /p/files`（HTML）返回 200 壳页——C12 把 `fs_capability` 从页面路由组迁到 `/ui/v1/files` 子路由后，页面从 403 变为 200 壳页 + 数据 403，与全站壳页一致，此行为变更此前无测试钉住。

### 3. 修正 4 处过时注释

- `crates/web/src/middleware.rs`：`check_fs_capability` 文档注释原写「`/{p}/files*` 页面与 JSON 接口」，改为「`/ui/v1/files*` JSON 接口 + 菜单入口隐藏」。

- （`middleware.rs` / `menu.rs` / `files.rs` 三处注释同步，消除「页面直达 403」的过期表述。）

### 4. 更新 4 处文档（统一为「壳页渲染 + 数据 403」）

## budding-boot.js 体积清理批次：SUBVIEW_TABS 迁到 Rust + 写操作模板提取

**背景**：`budding-boot.js` 已从 114KB 精简到 113KB（3139 → 3098 行），且发现两处重复模式：
1. JS 侧硬编码的 `SUBVIEW_TABS` 与 Rust 侧 `SUBVIEWS` 描述完全同一份三级菜单，两份表改一处漏一处；
2. 文件/运行环境/设置/站点写操作函数尾部高度重复（`submitJson → closeTopLayer → toast → reload → catch formError`）。

### 1. SUBVIEWS 双源合一（JS 删除硬编码）

- **Rust**：`routes.rs::Subview` 加 `blocked: &'static [&'static str]`（原先只在 JS 侧，`/sites/new` 这类路径要从 pattern 匹配里排除）；`get_routes` 响应新增 `data.subviews` 数组，把 Rust 侧三份 Subview（pattern / blocked / title / tabs）原样下发。
- **JS**：`budding-boot.js` 删除 `SUBVIEW_TABS` 硬编码表（约 25L），改为从路由表响应读 `subviews` 数组（类似 `pluginMeta` 的加载方式）；`matchSubviews` 循环体不变，迭代源从 `SUBVIEW_TABS` 改为全局 `subviews`。
- **收益**：删 43 行硬编码 + 注释，**改三级菜单路径只动 `routes.rs`，JS 零成本同步**（消除"改服务端漏 JS 表"的维护风险）。

### 2. 写操作通用模板 `writePost`

- 新增基础设施函数 `writePost(path, payload, opts)`：封装 `guard → submitJson → success handler → catch` 模式，覆盖：
  - 可选 `opts.guard`（二次确认，不传默认 `Promise.resolve(true)`）；
  - 默认成功链路：`args.inLayer` 时 `closeTopLayer` + `toast(data.message || fallback)` + `location.reload`；
  - 默认失败链路：有 `ctx` 用 `formError(ctx, '操作失败：' + error.message)`，没有用 `toast('操作失败：' + text, 'error')`；
  - 特殊成功/失败用 `opts.onSuccess` / `opts.onCatch` 覆盖。
- 第一批接入：9 个文件操作函数（`fileMkdir` / `fileWrite` / `fileRename` / `fileRemove` / `fileCopy` / `fileChmod` / `fileChown` / `fileArchive` / `fileExtract`）。
- 第二批接入：设置类（`menuWrite` / `dockerSettingsWrite` / `uiThemeWrite` / `uiPresetApply` / `passwordChange` / `totpSetup` / `totpEnable` / `keyImport` / `keyRemove`）、运行环境类（`runtimeCreate` / `runtimeImagesWrite` / `runtimeAction` / `runtimeConfigWrite` / `runtimeNodeWrite` / `runtimePortWrite` / `runtimeFileWrite` / `runtimeExt` / `runtimePecl` / `runtimeClone` / `runtimeUnbind`）、Web 服务类（`webConfigWrite` / `webParamsWrite` / `webEnvAction`）、配额（`quotaWrite` 三分支）、Compose 编辑（`composeEdit`）。
- 删除死代码：`runtimeDone` / `runtimeFail`（10 个 runtime 函数的统一收尾，功能完全等价于 `writePost` 默认模式，迁移后无调用方）。
- **累计收益**：**从 52 个 submitJson 用户压缩到 3 个**（`dockerWrite` 53L / `siteWrite` 151L / `runtimeProbe` 12L），均因逻辑过特殊（多分支条件 reload / 条件跳转 / success↔warning 级别切换且不 reload）值得保留原样。

### 6. ctx 传递纠偏（重构后发现的 UX 回归）

运行环境写函数原来的 `.catch(runtimeFail)` 是 toast（顶部提示），重构时误传了 `ctx: ctx` 给 writePost，会走默认 onCatch 的 formError（表单内联错误）。修复 6 个函数去掉多余的 ctx：

- `runtimeImagesWrite` / `runtimeNodeWrite` / `runtimeFileWrite` / `runtimePecl` / `runtimeClone`：原来 catch 是 runtimeFail（toast），去掉 `ctx: ctx`。
- `webConfigWrite`：原来 catch 是 toast，去掉 `ctx: ctx`。

**行为保持**：只有原来就用 formError 的函数（`runtimeCreate` / `uiThemeWrite` / `file*` 系列 / `composeEdit`）保留 ctx 传递。其余全部走 toast 风格错误展示。

- `dockerWrite`（53L）：容器写操作有条件 reload + 条件 toast + 自定义 payload 映射，强行接 writePost 反而让代码更难读。
- `siteWrite`（151L）：站点写操作最大函数，多分支（新建/保存/启停/删除/域名/证书），条件跳转和条件 toast 密集；值得后续单独拆分但本批次不动。
- `runtimeProbe`（12L）：探测操作成功时可能返回 warning 级别 toast 且不 reload（与 writePost 默认行为冲突）；强行接入反而让代码更长。
- **文件体积**：gzip 后实际传输体积需部署时实测，当前只做了源码级静态清理。
