## CI 红：`config.toml` 走内核通道后被自身的受保护守卫拒掉（已修）

**现象**：`32ae048` 的 `单测（Linux）`（run 44882308098 / job 136780044046）1 例失败——`skiff-web` 的 `ui_settings_panel_update_keeps_csrf_and_admin_semantics`（`crates/web/tests/main_flow.rs:5126`）；合法保存面板设置返回 400 `shape.invalid`，文案为「替换 `<tmp>/config.toml` 失败: … 内核运行配置或数据目录受保护，不能覆盖写入（命中 `<tmp>`）」。同轮其余 job 全绿，`test-win` 未在该 workflow 中。

**根因**：上一轮把面板保存与启动期 `entry_prefix` 写回改走 `AdminFs::write_kernel`（`config.toml` 零直写），但内核通道复用同一个 `Fs`，而 `Fs::write` 的 `ensure_not_protected` 对**内核受保护前缀**（数据根、`config.toml`、TLS 材料）一律硬拒，不区分主体。于是内核想写自己的运行配置时被自己的守卫挡住——测试夹具把 `config.toml` 放在 `data_dir` 下命中了数据根，生产路径的 `config_path` 本身也在保护清单里，同样会失败（启动期只 `warn` 不致命，更容易被忽略）。不是用例口径问题，是通道改造漏了口子。

**改法**：
- `crates/fs/src/subject.rs`：`Principal` 新增 `kernel` 标记与 `Principal::kernel(user)`（= 无授权根限制 + 受保护写 + 可写内核受保护前缀）；`admin` / `plugin` 构造恒为 `false`，Web 与插件拿不到。
- `crates/fs/src/ops/mod.rs`：`ensure_not_protected` 增加 `Principal` 参数，`is_kernel()` 时放行；删除/改名/复制/恢复/chmod/chown/archive/extract 共 9 处调用点同步传主体。普通管理员与插件的硬拒口径不变。
- `crates/app/src/admin_fs.rs`：`write_kernel` / `remove_kernel` / `ensure_dir_kernel` 主体改为 `Principal::kernel(KERNEL_ACTOR)`。
- 用例：`crates/fs/tests/protected.rs` 新增「内核主体可写受保护前缀、普通管理员仍 403」；`admin_fs` 既有 `kernel_runtime_config_is_protected_but_other_etc_is_not` 补 `write_kernel` 写 `config.toml` 与数据根的断言。

**为什么**：内核受保护前缀保护的是「面板与插件不得误改」，内核自身维护 `config.toml` 与 `data/` 恰恰必须能写；把例外收在主体能力上，比在调用点逐路径白名单安全，也不会削弱对管理员/插件的拦截。

**验证方式**：本机 `cargo fmt --all --check`、`clippy -p skiff-fs -p skiff-app -p skiff --all-targets`、`clippy -p skiff-web --all-targets` 与 `xtask check`（通道 0 处直呼、文件写 96 处 / 13 文件，基线未变）通过；用例结果交 CI 的 `test` job 复验。

**背景**：延续前三轮内核架构体检（`docs/impl/KERNEL_ARCH_AUDIT.md`），本轮按「模块划分 / 职责边界 / 依赖关系 / 复用性 / 过度设计」五维全量复扫 18 个 crate + 官方插件体系。分层禁令（`policy`/`pkgfmt`/`wire` 不依赖 `store`/`docker`、`app` 不含路由与模板、进程执行只经 `skiff_host`、内核文件写只经 `AdminFs`）与四项单一来源（wire 协议常量、TOFU 判定、`Docker::execute` 分发、RBAC 矩阵）**全部复核通过**；本轮处理的是散落在各层的小口径缺陷与残留，结构性问题挂账见文末。

### 1. 功能性缺陷（3 项）

- **FTP 插件的站点身份与内核冲突**：`plugins/ftp/src/main.rs` 硬编码 `SITE_UID/SITE_GID = 1000`，注释却写「即 `skiff-model::SITE_UID / SITE_GID` 的值」——而 `crates/model/src/site.rs` 定义的是 **201000**。后果是 FTP 插件建账号时把站点文档根 `chown -R 1000:1000`，与容器内 PHP 进程（201000）**不是同一属主**，容器写不进站点目录。改为经 `skiff-plugin-common` 转出 `skiff_model::SITE_UID/SITE_GID`（`plugins/common` 已依赖 `skiff-model`，不新增依赖边）；同时删掉退化成常量包装的 `resolve_identity`（参数 `_site` 从未使用）。
- **`/ui/v1/files` 与遗留 `/{p}/files` 行为分叉**：新建目录与重命名两处，前者未调用 `restore_site_index_owner(_tree)`，后者调用了。同一操作在站点文档根下走新接口建的目录/改的名，**不归还站点身份**，PHP 进程同样写不进。`crates/web/src/handlers/ui/files.rs` 的 `files_mkdir` / `files_rename` 补齐，与遗留通道口径一致（改名用递归口径 `_tree`，其余用单点口径）。
- **loopback 旁路采信客户端可伪造的审计身份**：`crates/web/src/middleware.rs` 的 `PluginManagerUser` 在 loopback 分支读请求头 `x-skiff-internal-actor` 当审计用户名，而**全仓没有任何发送方**（CLI 自调 `plugin.rpc` 不带该头）。等于给本机任意进程开了一个「在审计里冒充任意用户名」的口子。改为固定 `local-cli`：loopback 判定本身用 peer IP（不经过可伪造的 `X-Forwarded-*`），是可靠的；请求头不可靠且无用途，直接不采信。

### 2. 验签收口到唯一实现

### 2. `AdminFs` 新增原语（语义差异写进注释）

- `write_kernel_mode`：正文原子替换 + 单独 `fs.chmod` 审计。脚本 0755、私钥 0600 不能只靠 umask。
- `chmod_kernel`：非 Unix 返回 `Unsupported`，通道层当成功——`test-win` job 要跑建站路径，权限位在部署形态（Linux）才有意义。
- `write_if_changed_kernel`：内容一致就不写、不刷 mtime（mtime 会被运行环境页当「何时被改过」展示）。
- `rename_kernel`：**两段式**（目标存在时先删后移，不是 POSIX 一次性替换），因此只用于「启用/停用配置」这类目标本不该存在的开关动作；证书这种「读不到就握手失败」的文件走原子替换。
- `copy_kernel`：保留权限位，目标必须不存在（克隆语义）。

### 3. 闸门升级：白名单 + 按文件计数

- 未登记文件出现直写 → 失败（新增回潮点）；

当前登记只有一项：`("catalog/mod.rs", 2)`。

## 口令恢复入口 + 验收脚本止血 + 迭代下载加固

上一轮通道收口后，`TEST_LEDGER` 里风险最高的一条是「管理员口令丢失后无官方恢复路径」——它不是洁癖项，而是**唯一会让装机用户彻底失去控制权**的缺陷（2026-11-17 验收实测撞上，当时只能靠「停服 → 清 `users`/`sessions` → 启服」的运维技巧恢复）。本轮补上产品能力，并把验收脚本与迭代下载两处「真实撞过的失败面」一起处理。

### 1. `skiff admin reset-password`（新增恢复路径）

- `crates/store/src/db/users.rs`：新增 `reset_password`。与既有的 `set_password` 只差 `must_change_password` 的取值，但这个差别是语义性的——自助改密是用户自己刚定的口令（清 0），重置是**别人**设的临时口令（置 1，强制首登改密）。会话失效不放在仓储层做（那是另一张表），由调用方显式 `revoke_all_sessions`。
- `crates/core/src/bootstrap.rs`：把首启写 `initial-admin.txt` 的那段抽成 `write_admin_password_file`，首启与重置共用一份格式——两处各写一遍会让 `accept.sh` 按 `^口令: ` 取口令的约定悄悄分家；`random_password` 提升为 `pub(crate)` 复用同一字符集。
- `crates/core/src/cli.rs` + `commands.rs` + `main.rs`：`admin reset-password [--user <名>] --yes`。
  - 两个前提分工明确：**root** 决定「能不能改库」（数据根 `root:root 0711`、库文件 0600），**`--yes`** 决定「知不知道这是破坏性操作」；缺任一都直接拒跑并给可照做的提示。
  - root 判定读 `/proc/self/status` 的 `Uid:` 第二列（effective uid），不引 `libc`——少一条依赖边，且非 Linux 平台直接拒绝，避免它变成「开发机上悄悄改库」的旁路。
  - 口令**不接受**命令行传入：那会进 shell history 与进程列表。一律生成随机口令（16 位、去混淆字符集）写入 `initial-admin.txt`（0600），只在终端打印一次。
  - 动作顺序：`reset_password` → `revoke_all_sessions`（忘记口令的人手上可能还留着旧 cookie，不清理等于没重置）→ 写口令文件 → 落 `admin.reset_password` 审计。
- `crates/store` 用例 `reset_password_forces_change_while_self_change_clears_it`、`crates/core/src/cli.rs` 用例 `parses_admin_reset_password`（默认目标 / `--user` / 不带 `--yes` 仍可解析 / 未知子命令报错）。

### 2. `deploy/accept.sh`：验收不再把机器带进「无已知口令」

B 组原本在 B3c 把口令轮换成 `skiff-accept-<epoch>`、B3d 断言 `initial-admin.txt` 已删除，就此收尾——机器从此没有任何已知口令。新增 **B3g**：用改密后的新会话把口令改回本轮使用的 `$PW`，验收后机器状态与之前一致，`--password` 复跑仍然有效。

### 3. `tools/iter.sh::cmd_fetch`：重试、代理与可诊断

原实现是单次 `curl --max-time 600`，2026-11-08 实测被重置后只能手工绕。改为：

- **每轮重新取签名地址再下**：下载地址是 GitHub 的带签名 redirect（几分钟过期），在远端循环重试同一个 URL 必然失败，所以重试循环放在本机、每轮重新 `gh_api` 取地址；
- `--retry 2 --retry-delay 2`：只覆盖瞬时错误，不依赖 curl 7.71 才有的 `--retry-all-errors`（测试机版本未知）；
- `ART_PROXY`（默认沿用 `GH_PROXY`）代理开关，代理地址需测试机可达；
- 诊断行打印 **host / HTTP 码 / 字节数 / 耗时**，三次失败后给三条排查指引（设代理 → 手工走 API 资产端点 → 确认 artifact 未过期）。

## 第二梯队：站点备份恢复 + 三处产品边界定稿

第一梯队收口后剩下的四项，本轮按「能落代码的落代码、该定稿的定稿」处理。四项里只有一项需要新代码（站点恢复），另外三项分别是**确认已实现**与**明确不做**——把"没做"写成决定，比留着含糊的待办更有价值。

### 1. 站点目录：详情显示路径 + 跳文件管理（不做浏览页签）

站点详情概览本来就有「站点目录」「文档根」两行，各带「打开文件管理」链接（`site.root_dir` / `site.index_dir` → `/{p}/files?path=<编码后路径>`，见 `site_page.rs::overview_section`）。本轮的产出是**定稿**：不再补 `GET /ui/v1/sites/{domain}/dir`、不加「目录」页签——文件管理已经是同一套 `AdminFs` 路径代数，再做一个站点维度的树是第二套授权入口。`SITE-07` 从「阻塞」改为按新口径验收（链接可达 + 越界 400）。

### 2. 站点备份「从归档恢复」（本轮唯一新功能）

**问题**：`builtin:site-backup` 一直在产出 `<data>/backups/sites/<域名>/<YYYYMMDD-HHMMSS>.tar`，但没有任何恢复入口——有备份、无恢复等于备份只是心理安慰。

- `crates/app/src/sites/backup.rs`（新增）：归档目录推导、**归档名白名单**（拒绝 `/`、`\`、`..`、前导 `.`、非 `.tar`）、按 mtime 倒序列出最近 N 份、`<时间戳>-pre-restore.tar` 命名。纯函数 + 单测。
- `crates/app/src/tasks.rs`：`check_restore_target`（站点/目录/归档存在性，**同步**快速失败）+ `restore_site`（三步 `tar` 作业）。三步顺序是硬约束：
  1. `tar -tf` 预检 —— 归档损坏时**一个字节都不动站点目录**；
  2. `tar -cf <ts>-pre-restore.tar -C <站点根> .` 快照 —— 没退路就不恢复；
  3. `tar -xf <归档> -C <站点根>` 解包 —— 同名覆盖，归档里没有的文件保留。
  作业目标复用 `builtin:site-backup:<域名>`：作业层按目标互斥，恢复不会和调度器正在跑的打包同时写同一目录。
- **非阻塞**：三步作业远超 `REQUEST_TIMEOUT`（30s）。所以命令层只做校验，然后 `tokio::spawn` 执行，接口返回 `started=true`（与「新建运行环境返回已提交安装任务」同一套 UX）；成功/失败写 `sites.restore` 审计，过程进任务中心。
- **恢复后必须让 nginx 生效**：归档含 `conf/` 与 `ssl/`，不重载就会变成「磁盘上是恢复后的配置、nginx 内存里还是恢复前的」，下一次 reload（任何配置保存、巡检）才突然切过去——包括把恢复时已停用的 vhost 重新停掉。故成功后调 `activate_nginx_locked()`（reload 优先、必要时重启），结果写进审计 detail；失败不掩盖恢复本身已成功。
- `crates/app/src/commands/site.rs`：`RestoreSite` / `RestoreStarted` / `restore`（`confirm` 必须等于域名，校验放在命令层，任何新入口都绕不过去）；`NAMES` 补 `restore`。
- `crates/app/src/actions.rs`：`SITE_RESTORE`（Admin，`dangerous=true`）。
- `crates/web`：`SiteBackupInfo` 增加 `archives`（名称/大小/时间已格式化）；`POST /ui/v1/sites/{id}/backups/restore`；备份页签新增「归档与恢复」卡片，逐条给「恢复」，确认框要求手输域名。
- `budding-boot.js`：`skiffSiteWrite` 增加 `op=restore`；成功后只 toast 不刷新（新快照还没生成），进度指向任务中心。`SHELL_VERSION` 30 → 31（D11 缓存契约）。
- 用例：`sites/backup.rs` 三条（名称白名单 / 排序与过滤 / 目录不存在返回空表）、`tasks.rs` 一条（穿越名、非 `.tar`、未知站点都被拒）；`TEST_MATRIX` 新增 SITE-21。

## CI 首轮失败修正：`ensure_dir_kernel` 漏判末级非目录 + DTO 冻结清单

提交 `cdcc330` 推上 CI 后「单测（Linux）」红两条，都在本轮改动面上，已修：

1. **`tasks::tests::db_vacuum_failure_names_task_action_and_next_step`（`cdcc330` 之前就红，`6005b8b` 引入的回归）**
   - 现象：`backups/db` 被同名普通文件占住时，任务报的是「生成数据库快照失败：sqlite: unable to open database」——把「目录建不出来」错报成「快照写不出」。
   - 根因：`AdminFs::ensure_dir_kernel` 往上找首个已存在的祖先就 `break`，末级本身存在（是文件）时 `missing` 为空、直接返回 `Ok(())`，`create_dir_all` 的 `ENOTDIR` 语义被吃掉。所有走通道建目录的调用点都受影响（站点目录、证书目录同理）。
   - 修法：进循环前加一道 `path.exists() && !path.is_dir()` 判定，返回「目标已存在但不是目录（同名文件占用）」。同时把 `db_vacuum` 的处置建议补上「若目标被同名文件占用，先移走或改名」。
   - 用例改写：原来用 `std::fs::create_dir_all(...).unwrap_err().to_string()` 取平台相关 errno 文案来比对；生产路径已不走 `std::fs`，改为断言通道自己的语义（`同名文件占用`）与下一步（`先移走或改名`），不再把 `os error 17` 写死。

2. **`ui_v1_key_response_shapes_are_frozen`（本轮新增字段带出）**
   - `SiteBackupInfo` 增加 `archives` 后没同步 DTO 冻结清单，`crates/web/tests/main_flow.rs` 的 `site detail backup` key-set 断言失败（这正是该测试存在的意义）。
   - 修法：冻结清单补 `archives`；`docs/sdui/SDUI_BUDDING_INTEGRATION/05-BRIDGE-PAGES-A.md` 的站点详情字段表同步补 `interval` / `time` / `archives[]`，并把写操作清单里的路径参数从 `{domain}` 更正为 `{id}`（代码一直是主键），补上 `/{id}/policy` 与 `/{id}/backups/restore`。
