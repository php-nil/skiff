## CI 红：`config.toml` 走内核通道后被自身的受保护守卫拒掉（已修）

**现象**：`32ae048` 的 `单测（Linux）`（run 44882308098 / job 136780044046）1 例失败——`skiff-web` 的 `ui_settings_panel_update_keeps_csrf_and_admin_semantics`（`crates/web/tests/main_flow.rs:5126`）；合法保存面板设置返回 400 `shape.invalid`，文案为「替换 `<tmp>/config.toml` 失败: … 内核运行配置或数据目录受保护，不能覆盖写入（命中 `<tmp>`）」。同轮其余 job 全绿，`test-win` 未在该 workflow 中。

**根因**：上一轮把面板保存与启动期 `entry_prefix` 写回改走 `AdminFs::write_kernel`（`config.toml` 零直写），但内核通道复用同一个 `Fs`，而 `Fs::write` 的 `ensure_not_protected` 对**内核受保护前缀**（数据根、`config.toml`、TLS 材料）一律硬拒，不区分主体。于是内核想写自己的运行配置时被自己的守卫挡住——测试夹具把 `config.toml` 放在 `data_dir` 下命中了数据根，生产路径的 `config_path` 本身也在保护清单里，同样会失败（启动期只 `warn` 不致命，更容易被忽略）。不是用例口径问题，是通道改造漏了口子。

**改法**：
- `crates/fs/src/subject.rs`：`Principal` 新增 `kernel` 标记与 `Principal::kernel(user)`（= 无授权根限制 + 受保护写 + 可写内核受保护前缀）；`admin` / `plugin` 构造恒为 `false`，Web 与插件拿不到。
- `crates/fs/src/ops/mod.rs`：`ensure_not_protected` 增加 `Principal` 参数，`is_kernel()` 时放行；删除/改名/复制/恢复/chmod/chown/archive/extract 共 9 处调用点同步传主体。普通管理员与插件的硬拒口径不变。
- `crates/app/src/admin_fs.rs`：`write_kernel` / `remove_kernel` / `ensure_dir_kernel` 主体改为 `Principal::kernel(KERNEL_ACTOR)`。
- 用例：`crates/fs/tests/protected.rs` 新增「内核主体可写受保护前缀、普通管理员仍 403」；`admin_fs` 既有 `kernel_runtime_config_is_protected_but_other_etc_is_not` 补 `write_kernel` 写 `config.toml` 与数据根的断言。

**为什么**：内核受保护前缀保护的是「面板与插件不得误改」，内核自身维护 `config.toml` 与 `data/` 恰恰必须能写；把例外收在主体能力上，比在调用点逐路径白名单安全，也不会削弱对管理员/插件的拦截。

**验证方式**：本机 `cargo fmt --all --check`、`clippy -p skiff-fs -p skiff-app -p skiff --all-targets`、`clippy -p skiff-web --all-targets` 与 `xtask check`（通道 0 处直呼、文件写 96 处 / 13 文件，基线未变）通过；用例结果交 CI 的 `test` job 复验。

**背景**：延续前三轮内核架构体检（`docs/impl/KERNEL_ARCH_AUDIT.md`），本轮按「模块划分 / 职责边界 / 依赖关系 / 复用性 / 过度设计」五维全量复扫 18 个 crate + 官方插件体系。分层禁令（`policy`/`pkgfmt`/`wire` 不依赖 `store`/`docker`、`app` 不含路由与模板、进程执行只经 `skiff_host`、内核文件写只经 `AdminFs`）与四项单一来源（wire 协议常量、TOFU 判定、`Docker::execute` 分发、RBAC 矩阵）**全部复核通过**；本轮处理的是散落在各层的小口径缺陷与残留，结构性问题挂账见文末。

### 1. 功能性缺陷（3 项）

- **FTP 插件的站点身份与内核冲突**：`plugins/ftp/src/main.rs` 硬编码 `SITE_UID/SITE_GID = 1000`，注释却写「即 `skiff-model::SITE_UID / SITE_GID` 的值」——而 `crates/model/src/site.rs` 定义的是 **201000**。后果是 FTP 插件建账号时把站点文档根 `chown -R 1000:1000`，与容器内 PHP 进程（201000）**不是同一属主**，容器写不进站点目录。改为经 `skiff-plugin-common` 转出 `skiff_model::SITE_UID/SITE_GID`（`plugins/common` 已依赖 `skiff-model`，不新增依赖边）；同时删掉退化成常量包装的 `resolve_identity`（参数 `_site` 从未使用）。
- **`/ui/v1/files` 与遗留 `/{p}/files` 行为分叉**：新建目录与重命名两处，前者未调用 `restore_site_index_owner(_tree)`，后者调用了。同一操作在站点文档根下走新接口建的目录/改的名，**不归还站点身份**，PHP 进程同样写不进。`crates/web/src/handlers/ui/files.rs` 的 `files_mkdir` / `files_rename` 补齐，与遗留通道口径一致（改名用递归口径 `_tree`，其余用单点口径）。
- **loopback 旁路采信客户端可伪造的审计身份**：`crates/web/src/middleware.rs` 的 `PluginManagerUser` 在 loopback 分支读请求头 `x-skiff-internal-actor` 当审计用户名，而**全仓没有任何发送方**（CLI 自调 `plugin.rpc` 不带该头）。等于给本机任意进程开了一个「在审计里冒充任意用户名」的口子。改为固定 `local-cli`：loopback 判定本身用 peer IP（不经过可伪造的 `X-Forwarded-*`），是可靠的；请求头不可靠且无用途，直接不采信。

### 2. 验签收口到唯一实现

- `crates/app/src/catalog/verify.rs` 自己重写了一遍 Ed25519 验签，绕过 `skiff-sign` crate——而该 crate 的存在目的正是「商店清单签名协议的唯一实现」（内核与发布工具共用一份）。改为调用 `skiff_sign::verify_manifest_signature`，本地只保留清单层的三项前置一致性检查（算法名 / 清单 key_id 与公钥对应 / 签名与清单 key_id 对应）。
- 随之 `ed25519-dalek` 在 `skiff-app` 只剩测试用途，从 `[dependencies]` 移到 `[dev-dependencies]`。

### 3. 死代码与空抽象清理（净 −364 行）

- **删除 `crates/app/src/attention.rs`（195 行，零调用方）**：该模块是「概览页待办判定下沉」的产物，唯一消费方是旧 SSR 概览页；`b6a3e35`（删除旧 SSR UI）已把消费方删掉，模块成为孤儿。`/ui/v1/overview` 走的是自己的计数口径，不经过它。
- **删除 `skiff-sched` 的 `Executor` trait**：只有它自己的测试实现过，生产路径（`app/src/tasks.rs` 的 `drive_sample`）直接调插件 RPC 回填 `sched`，从不经过该抽象；其文档注释声称「真正的 async 插件 RPC 在 `skiff-core` 里用 `Executor` 包一层」，而 `skiff-core` 从未实现它——注释与事实不符，一并改正。测试改为直接构造 `ExecOutput` 断言调度器的水位往返契约。
- **删除 `skiff-plugin` 的 `FirewallHost` trait 与内核侧 `KernelHost` 实现**：`dispatch` 的 `host` 参数是 `_host`（带下划线前缀 = 明确不使用），防火墙能力面已整体迁到插件侧 exec 能力面，dispatch 对所有方法统一返回迁移提示。trait、`CommandOutput`（与 `ftp.rs` 重复定义）与内核 22 行实现一并删除；`FtpHost` 保留（`ftp::dispatch` 真的在用它）。
- **删除 `runtime_catalog` 的三个零调用方公开函数**：`default_php_image` / `extension_category` / `allocate_rust_port`。其中 `allocate_rust_port` 只有一个包装测试，测试改为直接测底层 `allocate_port(KIND_RUST, …)`，端口分配逻辑本身不受影响。
- **删除 `crates/web/src/handlers/sites/crud.rs`（13 行）**：名为 crud、实为一个纯文案函数 `save_config_notice`，与 `handlers/sites.rs` 的其它文案函数同级同性质，合并回 `sites.rs`。
- **删除 `views/sites.rs` 的三个死字段**：`alias_preview` / `alias_more` 只在构造处赋值、无任何读取方（SSR 退场后的残留）；`created`（SSR 格式串）同样无人读，web 侧只用 `created_at_epoch` 转 RFC3339。`aliases_text` 保留——列表关键字过滤真的在用它。

### 4. 重复实现收口

- **暂存文件清理**：`commands/store.rs` 与 `commands/upgrade.rs` 各写一份近乎逐行相同的 `cleanup_stale_incoming_at`（规则完全一样，只差扩展名白名单：商店 `.wbpkg`/`.part`，升级 `.tar.gz`/`.part`）。抽到 `crates/app/src/commands/incoming.rs` 的 `cleanup_expired(dir, now, ttl, extensions)`，两处只声明自己的扩展名集。新增三个用例：只删超龄且命中扩展名的普通文件（目录与非暂存文件不动）、时钟回拨时保守跳过、目录不存在不报错。
- **运行环境机型清单**：`catalog/model.rs` 校验商店清单时硬编码 `["php","node","rust"]`，与 `runtime_catalog::RUNTIME_KINDS` 是两份独立清单——新增机型漏改一处，商店就会拒收合法条目。改为调 `runtime_catalog::kind_def()`。
- **本地时间格式化**：`web` 层三处各写一份「本地时区 + 占位符」的 `fmt_ts`（`handlers/jobs.rs` 两份、`handlers/sites/tls.rs` 一份），格式串不同但语义一致。抽到 `web/src/util.rs` 的 `fmt_local_time(ts, fmt, fallback)`；歧义区间（夏令时本地时间有两个合法解）统一回落占位符，不显示可能差一小时的时间。

### 5. 依赖与分层复核（无违规）

- 依赖方向：`policy` / `pkgfmt` / `wire` 的依赖表与 `Cargo.lock` 解析结果均不含 `store` / `docker`（含间接依赖）；`model` 零 workspace 内部依赖，`sched` 不反依赖 `app`。
- 通道唯一：`xtask check-channel` 通过——`app`/`core` 非测试代码无 `Command::new`；内核文件写 **95 处 / 14 文件**（基线 96，只减不增，净减 1 处来自清理逻辑合并）。
- 单一来源：`skiff-wire` 协议常量、`plugin::trust::resolve` TOFU、`Docker::execute` 分发、`skiff_model::Permission` 角色矩阵，四项复核通过，未发现新的绕过点。

## 内核文件写通道收口：95 处 / 14 文件 → 2 处 / 1 文件

`KERNEL_ARCH_AUDIT.md` §3 的唯一未闭环项（「内核文件写通道外仍有生产写」）本轮处理完毕。首轮只迁了站点 vhost / 默认站点 / 环境脚手架三处热点，其余一直挂在审计 §3；这次把生产路径上的直写全部走完，并顺手把闸门从「计数只减不增」改成能真正防回潮的白名单。

### 1. 迁移面

- **站点生命周期**（`sites/crud.rs`）：建站目录与文档根 / 探针文件、vhost 写与删、启停 `rename`、默认站点投影与删除、`nginx -t` 候选目录与文件、`save_site_vhost` 写入与两处回滚、自签与上传证书的清理。证书发布改「读临时件 → `write_kernel_mode` → 删临时件」而不是 `rename_kernel`——见下节语义差异。
- **运行环境**（`sites/runtime.rs`、`sites/spec.rs`）：PHP/Node 目录、FPM pool、`entry.sh`、PHP ini 与扩展安装器、克隆复制（逐文件 `copy_kernel`）、停用 vhost、运行环境删除（`remove_tree_kernel`）。
- **nginx 主配置**（`nginx.rs`）：主配置写入、候选文件写入与发布、两处回滚；`CandidateFile` 从「存 PathBuf」改成「存 `Arc<AdminFs>` + PathBuf」，`Drop` 里的清理也留审计。
- **日志轮转**（`sites/logs.rs`）：`rotate_if_large` / `rotate_logs` / `rotate_site_logs` 全部接收 `&AdminFs`，轮转用 `rename_kernel` + `write_kernel(path, b"")` 截断。
- **商店缓存**（`catalog/store.rs`）：`save` 全量走通道，删掉本地那份 `write_atomic`。
- **暂存件清扫**（`commands/incoming.rs`、`store.rs`、`upgrade.rs`、`plugin.rs`）：`cleanup_expired` / `cleanup_stale_incoming` 改收 `&AdminFs`；验签失败与升级失败的清理走 `remove_kernel`；请求体与 CLI 安装路径补 `admin_fs` 传递。
- **内置任务与 Docker**：`tasks.rs` 的 `db_vacuum` 备份目录、`docker_daemon.rs` 的 `daemon.json` 目录。

### 2. `AdminFs` 新增原语（语义差异写进注释）

- `write_kernel_mode`：正文原子替换 + 单独 `fs.chmod` 审计。脚本 0755、私钥 0600 不能只靠 umask。
- `chmod_kernel`：非 Unix 返回 `Unsupported`，通道层当成功——`test-win` job 要跑建站路径，权限位在部署形态（Linux）才有意义。
- `write_if_changed_kernel`：内容一致就不写、不刷 mtime（mtime 会被运行环境页当「何时被改过」展示）。
- `rename_kernel`：**两段式**（目标存在时先删后移，不是 POSIX 一次性替换），因此只用于「启用/停用配置」这类目标本不该存在的开关动作；证书这种「读不到就握手失败」的文件走原子替换。
- `copy_kernel`：保留权限位，目标必须不存在（克隆语义）。
- `remove_tree_kernel`：目录递归删 + 6 次退避重试（Windows 上杀软占用会报 os error 145）。

### 3. 闸门升级：白名单 + 按文件计数

原规则「总数只减不增」有个漏洞：把 A 文件的两处删掉、在 B 文件新增两处，总数不变但回潮照样通过。改成 `xtask/src/main.rs` 的 `FS_WRITE_ALLOWED: &[(&str, usize)]`：

- 未登记文件出现直写 → 失败（新增回潮点）；
- 登记文件处数**超过**登记值 → 失败（本该收口的地方又长了）；
- 登记文件处数**低于**登记值 → 也失败（迁移后忘了下调登记，白名单会慢慢变成摆设）。

当前登记只有一项：`("catalog/mod.rs", 2)`。

### 4. 唯一保留的例外（C15）

`catalog/mod.rs` 的流式下载正文落盘与发布替换仍是 `std::fs`：`skiff-fs` 单次写上限 `MAX_REQUEST_BYTES = 256 KiB` 且无流式接口，包可达数十 MB；发布又必须一次性 `rename`（通道改名对已存在目标是先删后移，会给已校验产物多留一个「目标不存在」的窗口）。两处都在验签与摘要核对之后，失败即整包丢弃。重启条件写进 `KERNEL_ARCH_AUDIT.md` C15。

### 5. 顺带清理

- `sites/layout.rs` 的本地 `write_if_changed` 与 `remove_dir_all_retry` 上移进 `AdminFs`；`sites.rs` 的 `restrict_mode` 迁移后零调用方，删除。
- `crud.rs` 两处逐行相同的回滚闭包合并为 `restore_conf_snapshot`。
- `atomic.rs` 的 `write_atomic` 零调用方删除（原子替换与属主/权限位保留已由 `skiff-fs` 的 `preserve_attrs` 负责，其中 `fchown` 保留 uid/gid 正是原先 `lchown` 那段的目的），`app` crate 的 `libc` 目标依赖随之移除；`atomic.rs` 只留 `sibling_temp`（证书临时件命名）。`tasks.rs` 的 `io_hint` / `io_builtin_error` 随 `db_vacuum` 改造失去调用方，删除。
- 文档口径同步：`KERNEL_ARCH_AUDIT.md` §1/§3/§4-C15、`AGENTS.md` §4.1、`docs/sections/03-architecture.md`、`docs/sections/08-engineering.md`、`docs/plugin/HOST_EXEC_DESIGN.md`、`docs/contract/KERNEL_FS_CONTRACT/01-MODEL.md` 里「96 处 / 13 文件、只减不增」的旧描述全部改成白名单口径。
