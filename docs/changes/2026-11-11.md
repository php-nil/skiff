## PHP 扩展安装支持 Debian / Alpine 两家族

`db7e579` 上机复验发现：Debian 系站点提交 `runtime.ext.install` 立即
`failed exit_code=2`，日志 `sh: 5: cannot create /etc/apk/config: Directory nonexistent`。
根因是扩展安装脚本的 prelude 无条件写 Alpine 的 `/etc/apk/config`，`set -e` 在第 5 行中止。

### 改动（`crates/app/src/runtime_catalog.rs`）

- `installer_prelude`：`/etc/apk/config` 的写入包进 `command -v apk` 守卫，Debian 镜像不碰该路径；
  日志文案改为按分支说明（Alpine 下已启用 apk 包缓存）。
- 新增 `debian_build_package`：把扩展的 apk 依赖名映射为 Debian `-dev` 包
  （`postgresql-dev → libpq-dev`、`libjpeg-turbo-dev → libjpeg62-turbo-dev`、
  `freetype-dev → libfreetype6-dev`、`imagemagick-dev → libmagickwand-dev`、
  `gmp-dev → libgmp-dev`、`pkgconf → pkg-config`、`libxslt-dev → libxslt1-dev`、
  `openldap-dev → libldap2-dev`、`net-snmp-dev → libsnmp-dev`、`tidyhtml-dev → libtidy-dev`），其余同名。
- 新增 `legacy_deps_branch`：容器内按 `command -v apk` / `apt-get` 分支，不在宿主侧按镜像标签猜。
  Alpine 保持「运行库显式安装 + `.skiff-build` 虚拟构建包 + 编译后 `apk del`」；
  Debian 走 `apt-get update -qq && apt-get install -y --no-install-recommends` 装映射后的 `-dev` 包，
  不执行 `apk del` 式清理。两边都没有包管理器时明确报错并 `exit 3`。
- 单扩展（`legacy_install_script`）、批量（`batch_install_script`）、自定义 PECL 三条回退路径
  统一改用上述分支；清理步骤只在 `skiff_pm = apk` 时执行。
- 扩展目录与 ini 目录经核查走 `docker-php-ext-enable` 与宿主挂载的 `conf.d-skiff`，两家族一致，无需改动。

### 测试

- 新增 `extension_scripts_branch_on_container_package_manager`：断言 gd 与自定义 PECL 都含
  `command -v apk` / `elif command -v apt-get`、Debian `-dev` 映射、`DEBIAN_FRONTEND=noninteractive`、
  Alpine-only 清理与「既没有 apk 也没有 apt-get」报错。
- 更新 `installer_prelude_enables_apk_package_cache`：`/etc/apk/config` 写入位于 `command -v apk`
  守卫内且早于 `SKIFF_LOCAL_IPE=`。
- 更新 `runtime_libs_are_installed_explicitly_before_cleanup`：运行库安装仍先于 `.skiff-build`。

## `PHP_INI_SCAN_DIR` 去掉前导冒号，避免扩展 ini 重复加载

`a735a91` 的 SITE-15 上机复验仍 FAIL，根因在 `crates/app/src/sites.rs`：
`PHP_INI_SCAN_DIR = ":/usr/local/etc/php/conf.d:/usr/local/etc/php/conf.d-skiff"`
的前导冒号让 PHP 追加编译期默认扫描目录，而官方镜像的默认目录就是 `conf.d`，
同一目录被扫两次、扩展 ini 重复加载；`install-php-extensions` 的 `checkModuleWorking`
看到 `Module already loaded` 判失败，主路径 exit 1 后回退依赖表，pecl 已装过又返回非 0，
任务最终 `exit_code=1` 且扩展未 enable。纯内置扩展（zip/intl/bcmath）不经过该检查，故正常。

### 改动

- 常量改为 `/usr/local/etc/php/conf.d:/usr/local/etc/php/conf.d-skiff`，两个目录各扫一次，
  不再使用「沿用默认」语义；新增 `CONTAINER_PHP_CONFD` 常量避免路径重复书写。
- 全仓库只有 `php_spec_for` 一处消费该常量，没有其它逻辑依赖前导冒号。

### 测试

- 新增 `php_ini_scan_dir_lists_each_directory_once`：断言无前导冒号、无空段、两目录唯一且顺序为
  `conf.d` 在前，并断言 `php_spec_for` 注入的容器环境变量与常量一致。
- 容器内「扩展只加载一次」需上机验证（本机无 Docker）：`docker exec … php --ini` 两个目录各一次、
  无 `Module already loaded`，已写入 TEST_MATRIX SITE-15。

## FTP 新建文件权限与 `align_tree` 对齐

上机发现 FTP 上传文件 `0775`、新建目录 `2775`，而 `align_tree` 归一是文件 `0664`、
目录 `2775`：同一棵 `index/` 的权限取决于「有没有跑过 align」。

- 根因：pure-ftpd 以 `0777` 为基准减 umask（**文件也吃这个基准**，不是 0666）。
  `Umask = 002 002` 下文件落成 `0777 & !002 = 0775`。
- 修复：`Umask` 改为 `113 002`（文件掩码在前；Debian wrapper 要求两个空白分隔的三位
  八进制数，由它拼成 `-U 113:002`）。文件 `0777 & !0113 = 0664`；目录仍是 `0775`，
  继承父目录 setgid 后为 `2775`，与归一结果同形，新建即一致。
- `align_tree` 的权限计算抽成纯函数 `normalized_mode(is_dir, old)`，单测断言
  umask 推导结果与归一目标相同、且归一幂等（目录 `2775`、普通文件 `0664`、可执行文件
  `0775` 再跑不变）。契约 §4.3 与测试矩阵 FTP-01/FTP-04 同步。

## `sh install.sh` 的 `Bad substitution` 归属与调用姿势固化

上机 `sh install.sh --no-docker` 末尾报 `Bad substitution`。审计结论：仓库内 8 个
`deploy/**/*.sh` 全部 `#!/bin/sh`，无 `${PIPESTATUS[@]}` / `[[ ]]` / 数组 / `local` /
`+=` / `${var^^}` 等 bashism；`git log --all -S'PIPESTATUS'` 在全部历史中无命中，
`deploy/pack-release.sh` 只是原样拷贝 `install.sh`。报错来自**外层包装脚本**用管道接
安装输出后取 `${PIPESTATUS[0]}`（`docs/TEST_ENV.md` 已有同一记录），非仓库脚本缺陷。

## 站点配置 reload 优先与证书成对写入一致性

**reload 优先**（`crates/app/src/sites/crud.rs`）：`save_site_vhost` 原先每次保存都
`Verb::Restart` nginx，4 会话并发 254 次里有 29 次撞上重启窗口，误报「配置已回滚：
nginx 未能保持运行」，且每改一次 vhost 就断一下服务。改为：

- 在线容器先 `nginx -s reload`（失败依次回退 `openresty -s reload`、按
  `/var/run/nginx.pid` 发 `kill -HUP`）；
- reload 是否生效用 **worker PID 换代**自证：master 只有成功读完新配置才会拉起新
  worker，读失败时旧 worker 继续服务、PID 集合不变；50ms × 20 轮仍未换代即回退重启；
- 容器未运行、reload 失败、或 reload 后未换代才回退 `restart`；
- 失败语义不变：校验不过仍返回 `Conflict` + 差异，reload/restart 都起不来仍回滚
  文件并返回 `Unavailable`「配置已回滚到保存前内容：…」，回退重启后的存活检查与
  文案保持原样。
- `apply_tls` 同步改为 reload 优先，证书变更不再重启容器。

**证书成对写入**：`upload_cert` / `generate_self_signed` 原先两次独立 `rename`，
中间窗口被 nginx 读到会出现 `key values mismatch`。新增进程内锁
`skiff_app::sites::nginx_write_lock()`：

- 写对的一方持锁完成「cert+key 两次 rename + reload」；
- 保存 vhost、TLS 变更、`validate_nginx`、`restart_nginx`、站点解绑、巡检
  `nginx -s reopen` 都先取同一把锁；
- `replace_cert_pair` 在私钥 rename 失败时删掉刚换上的新证书（回到「无证书」而
  不是不配对）；自签证书先生成到唯一临时名，openssl 生成期间不占锁。

**测试**：`sites/tests.rs` 新增 `nginx_activation` 模块，覆盖 reload 优先（不重启）、
worker 未换代回退重启、停止容器直接重启、48 并发保存零重启且坏配置仍失败、
证书替换失败不留不配对组合。

  `--http` 是显式开关且与证书互斥，启动打印「仅测试用，无 TLS 与证书校验」。
  自签证书给 openssl 命令，客户端用 `[catalog].ca_bundle` 指向该 CA（§4.5 语义）。
- 路径：`/channels/<ch>/manifest.json`、`.sig`、`index.json` + `/blobs/sha256/<hex64>`；
  另支持 `/<ch>/...` 短别名；**不支持 `cur`/`latest`**（ETag 与缓存会随「当前最新」漂移，
  也无法与 `seq` 单调校验稳定对应）；`/api/**` 当前一律 404 且不属于本契约。
- 语义：仅 GET/HEAD（其他 405 + `Allow`）；强 ETag `"sha256:<hex>"`、`If-None-Match` 强比较
  → 304、无 INM 时 `If-Modified-Since`；JSON `application/json; charset=utf-8`、blob
  `application/octet-stream`；`Content-Length` 必带（304 除外，HEAD 与 200 同）；单区间
  Range → 206 + `Content-Range`，多区间与 HEAD 忽略，非法/越界 → 416；
  JSON/`.sig` 为 `no-cache`，blob 为 `public, max-age=31536000, immutable`。
- 安全：一次百分号解码后拒绝 `..`/`.`/空段/`\`/NUL，拼出路径 canonicalize 后必须在根内
  （符号链接逃逸同样 404）；只服务白名单普通文件；blob 名必须 `^[0-9a-f]{64}$`；无目录列表。
- 演进：路径稳定、只增不删；改 ETag/304/416 语义属破坏性变更，须同时改本节、实现、
  客户端与 TEST_MATRIX。

### 实现（`tools/skiff-server/src/serve.rs`）

- 复用既有 rustls/ring（经 `ureq::rustls`，与客户端同版本），未引入 axum/hyper；
  std `TcpListener` + 每连接一线程、`Connection: close`，无 keep-alive/HTTP2/压缩。
- `resolve` 做路径白名单与百分号解码；`respond` 按「方法 → 白名单 → canonicalize 包含性
  → 条件请求 → Range」返回；blob 直接从文件区间流式输出，JSON 读入并现算 sha256 作 ETag
  （超过 16MiB 按 500，产物 JSON 只有几十 KB）。
- 错误体只回固定短文本（`not found` / `method not allowed` / `internal error`），不回显路径；
  不返回 `Server` 版本头。

## Release 流水线产出 `skiff-server` 裸二进制

测试机没有 Rust 工具链，`serve` 之前只能在开发机跑。现在 release 流水线在既有两个 musl
静态 job 里一并编出分发侧二进制，随 Release 发布，测试机直接下载运行。

### 改动

- `.github/workflows/release.yml` 的 `build` 矩阵新增一步：
  `cross build --release --locked -p skiff-server --bin skiff-server --target <target>`，
  产物按 `dist/skiff-server-<target>` 命名（与安装包同轮构建、同一套静态链接自检）；
  amd64 额外跑一次 `--help` 冒烟，arm64 只做 `readelf` 静态检查（不引 qemu）。
- `publish` 的 Release 级 `checksums.txt` 从只覆盖 `*.tar.gz` 扩到 `*.tar.gz skiff-server-*`，
  `sha256sum -c checksums.txt` 对两类资产都成立；资产上传仍走 `find dist -maxdepth 1 -type f`，
  不需要固定清单，多出文件不会让 publish 失败。
- 该二进制**不进** `install.sh` 的安装包，也不装到 `/usr/local/bin`：它是运维侧分发工具，
  和面板主机上的运行物没有耦合。

### 文档

- `docs/SKIFF_SERVER.md` §16 补充定位：`serve` 是**测试与自建分发用**，正式对外分发由后续
  部署形态决定（Docker 或 systemd 托管同一批静态产物），不是唯一形态；§16.1 给出取二进制与
  `sha256sum -c` 的命令。
- `docs/CI.md` §2 工作流职责与 §4.4 资产清单补 `skiff-server-<target>`，并说明汇总摘要覆盖两类资产。

  不要整文件 `-c`」与资产用途。
