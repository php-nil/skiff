## 后台端口 / 入口前缀 / TLS 可配置（含三态 Cookie）

- 配置结构（单一来源，不拆两套）：
  - `Config` 新增 `tls_enabled: Option<bool>`（三态）、`entry_prefix: Option<String>`、`tls_active: bool`；
    `FileConfig` 同步，环境变量 `SKIFF_TLS_ENABLED`（`true/false/on/off/1/0`）与 `SKIFF_ENTRY_PREFIX`。
  - `tls_enabled = true` 必须有 `tls_cert`/`tls_key`，缺失拒绝启动且报错可读（指出字段、提示改 `false`）；
    `tls_enabled = false` 直接明文，不读证书、不生成自签；不写 = 旧行为自动推断（loopback / 反代 / 拒绝裸奔）。
  - 入口前缀显式值（config / env）优先并同步库；未配时首启随机 8 位落库。已有部署不改入口。
- 三态 Cookie（`crates/identity` 侧按 `dev_http` 判定）：
  - TLS 开启 / 反代终止 TLS：`__Host-skiff_session` + `Secure`（不变）。
  - 直接明文（`tls_enabled=false`）：`skiff_dev_session`，无 `Secure`、无 `__Host-`，HttpOnly/SameSite 保留；
    浏览器 HTTP 下登录、改密可走通，不再依赖反代/转发进程。
  - `allow_insecure_http` 语义收窄为「直接明文监听」；`trusted_proxies` 仍是「反代终止 TLS 时采信哪些 peer 的
    `X-Forwarded-*`」。显式 `tls_enabled=false` 时两者不参与判定。
- 启动与页面：明文非 loopback 时日志打一行「明文 HTTP 监听：Cookie 已降级，仅限内网或反代之后」，
  设置页显示醒目告警；启动地址 scheme 由 `tls_active` 决定。
- 设置页（「设置 → 后台端口 / 安全入口 / TLS」，仅管理员）：
  - 读取/修改 `listen`、`entry_prefix`、`tls_enabled`、`tls_cert`、`tls_key`，POST 保存写回 `config.toml`。
  - 端口 1–65535、`TcpListener::bind` 占用探针（同当前监听视为自己占用）；前缀 6–32 位 ASCII
    字母/数字/`-`/`_`、首字符字母或数字、不得为 `/`、保留段（`api`/`healthz`/`static`/`assets`/`favicon.ico`/`robots.txt`）。
  - 写盘：按 key 原位替换、去重复键、`toml` 解析复验、临时文件 rename；保留注释与其他字段。
  - 生效方式：**重启生效**，页面明确提示，不静默失败。
  - 防锁死：旧前缀 24h 内 GET 302 到新前缀（`settings.security.entry_prefix_previous` +
    `..._previous_until`），窗口外 404；新前缀始终可用。
- 安装脚本：`--tls on|off`、`--tls-cert`、`--tls-key`、`--no-tls`、`SKIFF_TLS`；on 时复制证书到
  `/etc/skiff/tls/`（0600）并写 `tls_enabled=true`，缺证书可读报错；off 写 `tls_enabled=false` 并告警。
  `systemd` 的 `ReadWritePaths` 补 `/etc/skiff`，否则设置页写不回配置。
- 涉及文件：`crates/core/src/{config,server,main,bootstrap}.rs`、`crates/app/src/{lib,panel_settings}.rs`（后者新增）、
  `crates/web/src/{lib,middleware,handlers/settings,templates}.rs`、
  `crates/web/templates/settings.html`、`deploy/{install.sh,config.toml.example,systemd/skiff.service}`。
- 验证：`crates/core` 新增 `tls_enabled_without_cert_fails_readably`、

- 根因：`crates/web/static/files.js` 的 `apiUrl()` 用相对路径。页面 `/{p}/m/core/files` 下

- 回归：`crates/web/src/assets.rs` 新增 `files_js_builds_absolute_api_urls`，断言脚本内含绝对路径拼接。

## install.sh 启用 TLS 时把 `tls_key` 写成 `tls_cert`（P0）

- 根因：`deploy/install.sh` 的 `conf_set_str` / `conf_set_bool` 用普通变量 `conf=$1 key=$2 val=$3`
  接收参数；POSIX sh 没有 `local`，赋值落到全局。`apply_tls_config` 先调
  `conf_set_str ... tls_cert "$cert"`（函数内 `key` 变成 `tls_cert`），再调
  `conf_set_str ... tls_key "$key"` 时实参已是 `"tls_cert"`，最终写出 `tls_key = "tls_cert"`。
  服务启动直接报「TLS 文件不存在: tls_cert」并无限重启，`install.sh` 却打印「已启动」。
- 修复：两个函数的参数改用 `_conf` / `_key` / `_val`，不再污染调用方同名变量；行为与写入格式不变。
- 复验：把脚本拷到测试机、先把 `tls_key` 改成 `/bogus`，再跑 `--tls on` →
  `tls_key = "/etc/skiff/tls/privkey.pem"`、`systemctl is-active skiff` = active、
  `https://127.0.0.1:18080/healthz` 与 `https://10.10.15.4:18080/healthz` 均 200。

- 现象：`/<prefix>/containers` 列表在 430px 视口下整页可横向拖动，`documentElement.scrollWidth` 超过视口。

## `worker_connections` 调大后 `nginx -t` 持续告警（WEB-02）

- 现象：站点「Web 服务 → 配置」保存 `worker_connections=2048` 后页面提示成功，但容器内
  `nginx -t` 一直告警 `2048 worker_connections exceed open file resource limit: 1024`。
- 根因：主配置只写 `worker_connections`，没有显式 `worker_rlimit_nofile`；OpenResty 容器软
  NOFILE 默认 1024，master 进程继承软限制，于是 2048 超过限制。**不是写错文件，也不是 reload 被吞**：
  文件落在 `/www/nginx/nginx.conf`（`conf.d` 由它 include），restart 返回成功，告警照样存在；
  `nginx -t` 退出码仍为 0，此前页面只看退出码，把「带告警」当成了「完全成功」。
- 修复（`crates/app/src/nginx.rs`、`crates/web/src/handlers/nginx.rs`）：
  - `render_main_nginx_conf` 同步输出 `worker_rlimit_nofile max(worker_connections, 1024)`；
    下限 1024，避免调小 `worker_connections` 时反而压低 fd 上限。
  - `apply_nginx_main` 收集 `nginx -t` 的 `[warn]` 行随成功返回；`save_nginx_params` /
    `save_nginx_main` 页面在有告警时明确显示条数与原文，不再吞掉。
  - 保存顺序收敛为：候选文件独立 `nginx -t` → rename 替换 → restart → 300 ms 后核对容器
    仍在 running；任何一步失败都回滚旧配置并在页面报错（覆盖「Docker restart 返回成功但 master
    立即退出」这条静默路径）。参数应用失败时同时把库回滚到旧值。
  - 参数表单数字字段显式解析：`abc` 不再静默回退 1024/65，直接报「需为 64–65535 的整数」。
- 回归：`main_conf_sets_worker_rlimit_nofile_above_connections`（2048→2048、64→1024、仅一处）、
  `nginx_test_warnings_are_collected`、`parse_params` 非法/合法用例、`main_flow` 页面含
  `worker_connections` 断言。
- 上机（2026-11-08）：保存 2048 → 提示「已保存并通过 nginx -t」无告警；容器 `nginx -t` 干净，
  主配置含 `worker_rlimit_nofile 2048`；`docker restart skiff-web-nginx` 与 `nginx -s reload` 后复测仍无告警。

## 插件子进程日志转出与退出收口

- 修复：插件 stdout/stderr 原先统一丢到 `/dev/null`，启动横幅与崩溃信息在 journal 不可见。
- 改为管道逐行读取，经 `tracing` 转出：stdout→info、stderr→warn；单行 1 KiB 截断，
  每路 20 行/秒、突发 128，被限速时记一条 `suppressed` 计数。
- stderr 留 2 KiB 环形尾巴：拉起失败时写进错误详情、审计与插件状态；新一次拉起先冻结
  上一轮尾巴（`begin_run` 输出 warn），不会被新日志覆盖。
- `spawn` 的就绪等待同时轮询 `try_wait`，插件提前退出立即失败，不再空等 5 s。
- **上机（`ff5c774`）发现并修复**：外部 `kill -9` 子进程后 `running` 条目仍在，`ensure`
  直接把死 socket 交给 RPC，返回 400 `IPC 连接失败: Connection refused`，既不复活也不转出尾巴。
  新增 `reap_exited`：复用前先 `try_wait`，已退出则摘条目、收尾读取任务、状态回落
  `installed`，再由下一次 `spawn` 的 `begin_run` 把冻结尾巴写进 journal。
- 回归：`ensure_respawns_after_child_exit`（预置一个已退出子进程，断言 ensure 重新拉起且只拉一次）。
- 文档：`docs/sections/04-plugin-package.md`。
