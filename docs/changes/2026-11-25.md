# 2026-11-25 变更记录

## `skiff-server sync` 补同步版本清单

**背景**：2026-11-24 复审发现 `sync` 的六步只取三件套 + `schema/` + 被索引引用的 blob，
`channels/<channel>/runtime-index/<kind>.json` 不在其中。用 `sync` 建的下游镜像因此没有这几份文件，
面板取到 404 后回退内置副本 / 目录大版本——不报错，但「可选版本不随面板发版滞后」这件事在下游等于没做。

- `Source` 新增 `fetch_optional`：`DirSource` 缺文件、`HttpSource` 404/410 → `None`；其余状态码与传输错误
  仍是失败。区分是必要的——把一次 5xx 当成「主站撤了这份文件」，镜像就会静默删掉本地副本。
  `HttpSource::fetch` 与 `fetch_optional` 共用 `read_body`，单对象上限只写一次。
- 步骤 5/6 增加按 `RUNTIME_INDEX_KINDS`（`build` 那边同一个常量）取三份清单：内容有变化才写，字节直接落盘
  不重新序列化；主站明确没有的类型**删掉镜像残留**——`runtime-index` 不进签名链，留着等于对外发一份
  过期版本表，宁可让面板回退。`SyncReport` 相应增加 `runtime_index_written` / `runtime_index_removed`，
  CLI 只在有变化时多打一行。
- 步骤 6/6 自检增加：镜像里存在的每份清单必须过 `runtime-index.schema.json`，且 `kind` 与文件名一致、
  `channel` 与目标渠道一致。缺失不算错（主站可以只发布其中一类），内容坏了才算。
- 测试：`tests/sync.rs` 增「清单字节与主站一致、二次同步不重写、主站停发后残留被删」；`src/sync.rs`
  单测用一次性 TCP 服务覆盖 404 → `None`、500 → 失败。
- 文档：`06-RELEASE_MIRROR.md` §14.3（步骤表、只增不删的例外、自检口径、测试清单）、
  `07-SERVE.md` §16.2（删掉「下游整目录复制」的过渡口径）。
- 验证：`cargo fmt --all --check`、`clippy -p skiff-server --all-targets -- -D warnings` 通过；
  定向跑 `cargo test -p skiff-server --test sync`（7 项）与 `--lib sync::`（2 项）全通过。
  其余用例仍以 CI 为准。

## `check --builtin-index`：内置副本必须与产物字节一致

**背景**：面板内置副本 `crates/app/assets/runtime-index/php.json` 是服务端产物的快照，靠人工 `cp` 回填。
它一旦比产物新，面板的防回滚会把镜像服务清单**永久**判成「更旧」并拒用——页面只显示「已忽略」，
功能等于失效。此前这条只写在流程里，没有任何东西能挡住手写。

- `check::verify_builtin_index(dist, builtin_dir, channel)`：读产物树，把内置副本目录里的
  `php`/`node`/`rust` 清单逐个与 `channels/<ch>/runtime-index/<name>` 比 sha256；不一致打印两份摘要
  并给出「用产物覆盖」的提示。产物缺该文件也算失败（内置副本不能超前于产物）。
- CLI：`check --dist <dir> --builtin-index <dir> [--channel <name>]`。默认不启用（CI 用夹具产物，
  本来就不等于内置副本）；产物有多个渠道时必须显式 `--channel`；`--builtin-index` 缺 `--dist`
  直接报错。
- 测试：`tests/cli.rs` 增「字节一致通过 / 改一字节失败 / 缺 `--dist` 报错」。
- 文档：`06-RELEASE_MIRROR.md` §14.4（抽验步骤带上该旗标）、§14.5（代码落点与测试）、
  `SITE_RUNTIME_CONTRACT/02-CREATE_PAGE.md` §4.5（回填顺序后补一条校验命令）。
- `TEST_LEDGER` 的清单挂账只剩「真实条目数据」：字节一致不再靠人眼。

## `runtimes` 命令：从上游自动刷新版本清单

**背景**：清单的版本来源是人工维护的 `catalog/<channel>/runtimes/*.json`（每个版本一份，带 image 与
digest），内置副本还要人工 `cp` 回填。要一条命令自动取最新版本、把这几个 JSON 更新到位。

- 新增 `skiff-server runtimes`：版本与 EOL 取 `endoflife.date`（PHP 全部受支持分支、Node.js 只取
  已进 LTS 的、Rust 只取当前 stable，已 EOL 的不收）；镜像 tag 的 `sha256` 走镜像仓库 `v2` API，
  认证按 `WWW-Authenticate` 的 Bearer 挑战换 token 重试。
- **两阶段**：先只读预检（每类要选哪些版本、digest 拿不拿得到），再统一写盘。任一类「有目标版本但
  一个都拿不到 digest」直接退出且不写任何文件；个别版本失败只跳过它并打印原因。上游某类没有可用
  版本时不动旧条目（`--prune` 也不动手）——接口故障不该把整类删光。
- 写盘顺序：`catalog/<ch>/runtimes/<kind>-<version>.json` → `build` → 内置副本 `php.json`
  （取产物同一份字节）→ 可选 `--out` 整份产物。默认版本保持唯一：旧条目被保留时会把 `default` 摘掉。
  `--prune` 才删上游已不支持的旧条目，`yanked` 一律不动。
- `--dry-run` 不联网取 digest、不写文件，只列上游版本。本机实测：PHP `8.6.0 / 8.5.13 / 8.4.28 /
  8.3.37 / 8.2.36`、Node `26.13.1 / 24.22.3 / 22.23.5`、Rust `1.100.0`。
- 本机 Docker Hub 不可达，实测真跑走到「1 个目标版本都拿不到镜像摘要，未写任何文件」并确认临时
  catalog 里旧条目与 `default` 一字未动——失败路径是有效的。
- 测试：`tests/runtimes.rs` 6 项（含「全失败零写入」）+ 模块单测 6 项；`fmt` / `clippy -D warnings` 通过。
- 文档：`06-RELEASE_MIRROR.md` §14.4（新增）、§14.5 运维步骤加第 0 步、§14.6 落点与测试；
  `02-CREATE_PAGE.md` §4.5 指向该命令；`04-ROLLOUT.md` 状态表。

## `runtimes` 每分支保留三个版本（兼容性余量）

**背景**：原来每个发布分支只收 `latest` 一个版本，清单里 `8.5` 只有 `8.5.13`，老站点要降级时
选不到 `8.5.12` / `8.5.11`。改为默认每个分支保留最近三个版本。

- 规划拆成两步：`supported_cycles`（挑受支持分支，EOL 过滤不变）与 `desired_from`（把一个分支的
  版本列表展开成条目）。同一分支的补丁共用分支 EOL，版本号仍要求 1–3 段纯数字。
- `Upstream` 新增 `branch_versions(kind, cycle, per_branch)`，默认实现只回 `latest`（拿不到历史版本
  时宁可少给也不编造）；`HttpUpstream` 按类型补齐：
  - PHP：从 `latest` 逐个减补丁号问 `releases/index.php?json&version=`，以响应里的 `version` 字段
    为准（php.net 对不存在的版本仍回 200，正文是 `{"error":"Unknown version"}`）。
  - Node.js：`dist/index.json` 全量索引按 major 分组、版本降序取前 N（跨 minor，剔除非 `vX.Y.Z`）；
    索引一次拉取后缓存在 `HttpUpstream` 里。
  - Rust：`channel-rust-<ver>.toml` 的 200/404（用 HEAD，不下载近 1MB 清单）。
- 历史版本查询失败只降级为该分支的 `latest` 并记进跳过清单，不让整类失败。
- 新增 `--per-branch <n>`（1–4，默认 3；`1` 等价于只留最新）。上限取 4 是因为面板
  `PATCHES_PER_MAJOR = 4`，超过就是发了也显示不出来。
- 真实上游演练：PHP 13 条（`8.6.0`；`8.5.13/12/11`；`8.4.28/27/26`；`8.3.37/36/35`；
  `8.2.36/35/34`）、Node 9 条（`26.13.1/13.0/12.1`、`24.22.3/2/1`、`22.23.5/4/3`）、
  Rust 1 条（`1.100.0`，该分支只发过一个版本）。面板侧上限是每大版本 4 条，三条补丁都显示得下。
- 测试：`tests/runtimes.rs` 增至 8 项（新增每分支三版本、`--per-branch 1`、历史版本查询失败降级）；
  `src/upstream.rs` 单测增至 6 项（补丁号递减、Node 索引分组）；`fmt` / `clippy -D warnings` 通过。
- 文档：`06-RELEASE_MIRROR.md` §14.4（命令、每分支口径、数据源）、§14.6 落点与测试；
  `02-CREATE_PAGE.md` §4.5 补「每分支默认三个版本」与 `--per-branch`。

## 面板侧：补丁号按点号边界归入大版本（修复 Node 清单被整份丢弃）

**背景**：接上「每个分支三个版本」后发现，即使清单里写了 `24.22.3`，面板也会整份丢掉——两处
都拿「版本前两段」去和目录项比对，而 Node 的目录项是单段 `24`。

- `runtime_index::sort_and_trim`：`major_of("24.22.3")` 得 `24.22`，目录里只有 `24` → 全被当成
  未知大版本过滤，Node / Rust 清单只能回退目录大版本。改为「取目录项里最长的、等于它或作为其
  点号前缀的那一项」，`8.55.0` 不会被 `8.5` 误收。既有测试 `node_and_rust_tags_are_understood`
  （期望保留 `24.4.0`）因此由红转绿。
- `runtime_catalog::version_supported`：同一口径问题，`24.22.3` 提交会被判「版本无效」——面板
  给了选项却存不了。改为同样的点号边界匹配；`major_of` 随之没有调用方，删除。
- 测试：`runtime_index` 新增 `patches_under_a_short_cycle_still_match`（Node 跨 minor 共用 24 的
  四条上限、Rust `1.99.1` 归 `1.99`）；`version_catalog_is_dropdown_only` 改为断言 `24.22.3`
  通过、`21.1` 与 `2` 拒绝（`2` 不能被 `24` 前缀误收）。
- 顺带修 `create_validates_kind_and_version_before_docker`：「空版本被拒」与实现（空版本回落目录
  首项，契约明写留空用默认）矛盾，改用不在目录的 `9.9.9` 验证「校验先于 Docker」这一原意。
- 口径：面板每大版本上限 4 条（`PATCHES_PER_MAJOR`），三类每分支发 3 条都显示得下。
- 验证：`cargo test -p skiff-app --lib` 383 项全绿；`fmt --check` 与
  `clippy -p skiff-app -p skiff-web -p skiff-server --all-targets -- -D warnings` 通过。

## 走内网代理真跑 `runtimes`：真实条目落盘 + 两处出网缺陷

**背景**：上一次真跑卡在「拿不到镜像摘要」，当时结论是「本机 Docker Hub 不可达」。手册
（`docs/test/ITERATION/02-ISSUES_ENV.md`）里记着内网 HTTP 代理，实测 `10.66.10.22:1010`
到 `auth.docker.io` 返回 200 —— 真正的原因有两层，都不是「网络封了」。

- **`skiff-server` 不认 `HTTPS_PROXY`**：workspace 的 `ureq` 是 `default-features = false`
  + `features = ["tls"]`，`proxy-from-env` 没开，`AgentBuilder` 的 `try_proxy_from_env`
  因此恒为 false。curl / git 走代理能通，命令却不能，最容易误判成「仓库没发布 tag」。
  没有直接打开该特性：ureq 不读 `NO_PROXY`，开了会让本机 httptest 也走代理，设了代理的
  环境里 `tests/serve.rs` / `tests/sync.rs` 必红。改为显式旗标
  `runtimes --proxy <url>`（`HttpUpstream::with_proxy`），并在帮助与文档里写明不读环境变量。
- **Registry API 打错域名**：`split_image` 把 `php:…` 归成 `docker.io`，请求于是打到
  `https://docker.io/v2/…`，那是网页域名，301 到 `www.docker.com`，响应里没有
  `Docker-Content-Digest`。新增 `api_host()`：`docker.io` → `registry-1.docker.io`，
  其它 registry 原样透传；单测覆盖该映射。
- **失败信息带首个原因**：原来只说「N 个目标版本都拿不到镜像摘要」，现场分不清「tag 未就绪」
  与「代理配错」。现在 bail 里附上第一条 `skipped` 原因。
- **真实数据**（`--proxy http://10.66.10.22:1010 --prune`）：PHP 13 条
  （`8.6.0`；`8.5.13/12/11`；`8.4.28/27/26`；`8.3.37/36/35`；`8.2.36/35/34`）、
  Node 9 条（`26.13.1/13.0/12.1`、`24.22.3/2/1`、`22.23.5/4/3`）、Rust 1 条（`1.100.0`）；
  删掉假 digest 的占位 `php-8.5.json`；渠道 `generated_at` 由 `2026-11-09` 推进到
  `2026-11-25T10:07:00Z`（否则内置副本的防回滚基准会倒退）；内置副本回填为产物同一份字节。
  `check --dist … --builtin-index crates/app/assets/runtime-index` 通过。
- **目录对齐上游**（原挂账项，用户确认三类都对齐）：`RUNTIME_KINDS` 改为
  PHP `8.6 / 8.5 / 8.4 / 8.3 / 8.2`、Node.js `26 / 24 / 22 / 20`、Rust `1.100 / 1.99 / 1.98 / 1.97 / 1.83`。
  副作用：新站默认版本变为 PHP `8.6.0` / Node `26` / Rust `1.100`（清单 `default` 即最高版本）。
- **测试改为「按数据推导」**：真实条目进了同一份渠道目录，写死数字的断言全部失效——
  `p0` 的 `runtimes.len() == 1` 与硬编码 `generated_at`、`runtime_index_is_generated_per_kind`
  （先清空 `runtimes/` 再验「没条目就不落盘」）、`sync` 的 `runtime_index_written/removed == 1`、
  以及 `runtime_index` 单测里写死 `8.5.13` 的两处。改为按目录条目数与渠道时间戳推导，
  以后每次刷新数据都不用再改测试。
- 验证：`cargo test -p skiff-app --lib` 383 项、`-p skiff-web --lib` 114 项、
  `-p skiff-server`（lib 47 / api 36 / cli 6 / p0 18 / runtimes 9 / serve 8 / sync 7）全绿；
  `main_flow` 里与清单相关的 `ui_runtime_catalog_exposes_apk_mirrors_and_current_choice` 通过
  （其余 `budding_boot_*` 失败与本次改动无关，是工作区既有的 `应注册 code Pack` 一类断言）。
