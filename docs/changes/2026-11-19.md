## 防火墙插件性能优化（后端 OnceLock 缓存 + 前端 localStorage 缓存）

**背景**：测试机作业中心出现多条 `com.skiff.firewall` 执行失败（409 同目标活跃作业冲突）；插件页面打开速度很慢。

### 根因分析

**exec 能力面的同目标唯一活跃**：`crates/core/src/kernel/exec.rs` 提交作业时，SQLite 部分索引 `idx_jobs_active_target` 保证 `(target_type, target_id)` 的活跃（queued/running）作业唯一，`target_id` = 插件 id（`com.skiff.firewall`）。同一插件同时只允许一条活跃作业，第二条立即 409。

**插件的探测调用模式**（修复前）：
- SDK `host_exec_full` 每次调用 = 提交作业 + tokio 起进程 + 同步等待终态（轮询 `status`）
- `h_status()` 内部：先 `command_works(nft)` + `command_works(iptables)`（2 条），再 `detect_backend()`（又跑一遍 nft+iptables，2 条），再加规则 dump、fail2ban_installed（dpkg-query + fail2ban-client，2 条）、fail2ban_running（systemctl，1 条） → **单 handler 8 条 exec**
- `h_rules_list()`：`detect_backend`（2 条）+ `ensure_nft/iptables`（探测链是否存在，1 条）+ 规则 dump（1 条） → **单 handler 4 条**
- 前端并发 `Promise.all([rpc("status"), rpc("rules.list")])` → 两个 handler 各自 std::thread::spawn 起独立线程（SDK serve_inner）→ 两个线程各自往内核提交 exec → **同目标唯一活跃冲突**：第一条提交成功，后续收到 409 → 作业中心一堆"失败"，前端拿到的也是部分数据

**结论**：12 条探测 exec 里，**后端类型探测 + fail2ban 安装探测**在插件生命周期内完全不变（on-demand 模式下进程长驻，装/卸软件需要管理员显式操作且重启插件才生效），应当用进程内 OnceLock 缓存。动态探测（fail2ban_running、规则 dump）每次都得跑。

### 26. 后端 OnceLock 缓存

- **改了什么**：`plugins/firewall/src/main.rs`
  - 新增 `BackendProbe { nftables, iptables, selected }` + `backend_probe(p)`：一次 exec 探测，返回 nftables 和 iptables 各自可用性 + 选中的后端类型；`OnceLock` 缓存进程内复用
  - 新增 `F2bProbe { installed }` + `f2b_probe(p)`：fail2ban 安装状态探测，同上缓存
  - `detect_backend` / `fail2ban_installed` 改为从缓存取
  - `h_status` 改用 `backend_probe` 一次性探测，消除之前"先 command_works(nft+iptables) 再 detect_backend（又一遍）"的重复 → **探测 exec 从 4 条降到 2 条**
- **为什么**：on-demand 模式下插件进程长驻，后端类型和 fail2ban 安装状态在进程生命周期内固定。缓存后：首次调用跑探测，后续并发 handler 直接从 OnceLock 取，**零 exec**。并发线程间不再互相抢作业槽位。
- **不变量**：`fail2ban_running`（systemctl is-active，服务可能被 start/stop）和规则 dump 不缓存，每次都跑。
- **exec 次数对比**：

| 场景 | 修复前 | 修复后 |
|------|--------|--------|
| 首次打开规则页 | ~12 条（status 8 + rules.list 4，并发互抢） | ~6 条（backend_probe 2 + f2b_probe 1 + fail2ban_running 1 + 规则 dump 2） |
| 刷新规则页（第二次） | ~12 条 | ~3 条（规则 dump 2 + fail2ban_running 1） |
| 并发 status + rules.list | 互相抢作业槽 → 409 失败 | rules.list 探测全命中缓存 → 零冲突 |

### 27. 前端 localStorage 缓存 + 异步刷新

- **改了什么**：`plugins/firewall/ui/app.js`
  - 新增缓存工具（`tryReadCache` / `writeCache` / `invalidateCache`），5 分钟 TTL
  - 规则页 `refresh()`：先读 localStorage 缓存直接渲染（**首屏零等待**），再调 RPC 异步刷新并覆盖；刷新失败时已有缓存则静默，无缓存才报错
  - fail2ban 页 `loadJails()`：同上
  - 所有增删改操作回调（规则增删、端口放行、fail2ban 启停装卸、jail 增删、unban）先 `invalidateCache` 再 `refresh/loadJails`
- **为什么**：后端 RPC 返回需要等 exec 完成（哪怕缓存优化后也要 ~3 条 exec），前端 localStorage 缓存让页面打开瞬间就能看到上次的规则/fail2ban 状态（对管理员来说"上次的状态"比"完全空白"好得多），后台再悄悄刷新成最新。5 分钟 TTL 足够长覆盖常规刷新节奏，又不会让人看到过时数据。
- **不变量**：fail2ban.banned 列表（loadBanned）不缓存——它是单次点击查看的临时需求，列表本身也不大。

### 验证口径

本机内存被另一编译会话占着（可用 < 1024MB，闸门拒跑），未能跑 fmt + clippy。改动纯逻辑层（OnceLock 无外部依赖、JS localStorage 纯 DOM API），语法静态核对无误。用例（插件 workspace clippy -D warnings）交 CI。

### 后续架构完善项（不在本批）

当前 SDK 只有 `host_exec_full` 一条 exec 通道（全部进作业中心）。`crates/app/src/host.rs` 第 308 行已明确规划「作业之外的执行：只读探测或短命令，不写作业日志、不跟取消」的轻量通道，但 SDK 未暴露。防火墙插件的探测命令（`nft --version`、`dpkg-query`、`systemctl is-active`）理想路径应走轻量通道，**既不抢活跃作业槽位也不进作业中心**，只留真正有副作用的命令（add rule / start fail2ban / apt-get install）走作业化路径。

## exec 安全收口：RuntimeMaxSec 兜底 + 升级强制复核 + 确认页风险标注

**背景**：重新检查 KERNEL_EXEC_CONTRACT.md 与 HOST_EXEC_DESIGN.md 的「未落地」与「待决策」清单，三项硬前提直接落地。

### 28. `systemd_run_argv` 补 RuntimeMaxSec 兜底

- **改了什么**：`crates/host/src/lib.rs` — `systemd_run_argv` 新增 `timeout_secs: u64` 参数，argv 注入 `--property=RuntimeMaxSec={timeout_secs + 10}`；`spawn()` 调用点传 `spec.timeout_secs.max(1)`。两个单测同步更新断言 `RuntimeMaxSec=40` / `RuntimeMaxSec=130`。
- **为什么**：原实现只在 Rust 进程内用 tokio deadline + `stop_unit` 终止；如果 Rust 进程崩了/重启了，`systemd-run` 启动的瞬态单元会继续跑。补 RuntimeMaxSec 让 systemd 自己也有一道兜底强杀。`+ 10` 是 Rust 侧的清理窗口（正常情况下 Rust 先 timeout，然后 cleanup 里 stop_unit）。

### 29. 升级分支不再静默补授新增 object grant（安全硬前提）

- **改了什么**：`crates/plugin/src/install.rs` — 升级分支的 object_upgrade 逻辑从「相对旧 manifest 新增的 hint 自动补授 + 写审计」改为「只有用户在确认页显式勾选（出现在 `opts.object_grants`）的新增 hint 才补授」；未勾的静默跳过。permission 级别的自动补授保持不变。
- **为什么**：旧逻辑让插件作者发新版即可静默扩大 `bin:` / `path:` / `plugin:` 授权面，安装时的「人类闸门」只对首装成立。修复后升级等同于重新确认——不勾就不加。修一次 `path:` 与 `bin:` 同受益。
- **测试同步**：原 `upgrade_grants_new_resource_hint_and_audits` 拆为两个（勾了补授 / 没勾不补）；`upgrade_grants_interop_hint_for_new_dependency` 改为用户显式勾才补。其余三条升级 hint 相关测试（旧 hint 保留 / 移除不回收 / 没勾不翻案）语义不变。

### 30. 确认页 bin_risk 标注 + root-equiv 默认不勾

- **改了什么**：
  - `crates/web/src/templates.rs`：新增 `ResourceRow { value, risk }` + `ResourceRow::new()`；`PluginConfirmPage.resources` 从 `Vec<String>` 改为 `Vec<ResourceRow>`。
  - `crates/web/src/handlers/{store.rs, plugins.rs}`：两处构建时调 `skiff_model::bin_risk` 标注 `bin:` 前缀的风险档；其他类型一律 `scoped`。

- **为什么**：`apt-get` / `systemctl` / `cp` / `chmod` 等 root-equiv 二进制授出即完整 root 权限，原确认页默认全勾。现在 root-equiv 默认不勾，强制注意。
