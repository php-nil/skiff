## 首轮测试查出的两个缺陷：弹窗提交失败静默、插件拒装删源包

**背景**：budding 1.8.6 同步完成后按测试规范在干净测试机上跑一轮（首装 → `accept.sh` → 浏览器逐页），两个缺陷都是「编译、类型、静态断言全绿但用户能看见」的类型。

### 1. 弹窗提交失败什么也不显示（静默失败）

- **现象**：文件管理「新建目录」重名提交，弹窗不关、输入保留，但弹窗内没有任何错误文案，`console` 只有一条 409。表面看像「点了没反应」。
- **根因**：`formError` 只认 `ctx.extras.form`——那是表单族经 `ActionExtrasKey` provide 的「最近祖先表单」，只有动作位于表单子树内才存在。壳层弹窗的提交按钮在图层 **`footer`**，页脚与正文是两棵兄弟子树，`extras.form` 恒为空，于是每次都落到 `toast` 兜底（提示 2 秒即散，等于没有）。
- **修复**：`budding-boot.js` 抽出 `formOf(ctx)`，按 budding 自己的目标解析规则（契约 §8.3.2，与它的 `setErrors` 动作同一条）取控制器：先 `extras.form`，再 `extras['budding:layer-forms']` 登记表（`LAYER_FORMS_KEY`），唯一一张即用、多张不猜。`formError` 改为 `formOf(ctx)` + `setErrors` + `focusFirstError`，取不到才退回 `toast`。
- **用例**：`budding_boot_file_forms_send_typed_values_and_show_errors` 改为锁 `formOf` 的两档解析（`extras.form` / `LAYER_FORMS_KEY` / `registry.list()`）与 `LAYER_FORMS_KEY` 的字面量；`SHELL_VERSION` 44 → 45。
- **实测**：修复后同名建目录，弹窗内出现红色「新建目录失败：目标已存在」，输入值保留、图层不关；新建站点在 Web 服务未就绪时同样就地显示 503 原因。

### 2. 插件安装被拒时把源包删掉

- **现象**：测试机首装后逐个安装 8 个官方插件，全部因「要求完整沙箱」被拒；开着 `allow_reduced_sandbox` 重装时才发现 `/www/skiff/official/*.wbpkg` 已经被**清空**，只能从解包目录重新拷。
- **根因**：`crates/app/src/commands/plugin.rs::install` 在 `install_package` 返回后无条件 `kfs.remove_kernel(package)`。注释假设「暂存包是内核自己落下的中间产物」，但 CLI 的常见用法是直接把发行包自带的 `/www/skiff/official/com.skiff.<x>-<ver>.wbpkg` 交给它——那是装失败后重试的唯一副本，也是启动时比对官方版本做随包更新的来源。装成功时删它同样有害：官方包目录被逐个清空，自动更新随之失效。
- **修复**：只在**两条都满足**时清理——装成功 + 路径在 `data_dir/plugins/.incoming` 内（内核自己落下的暂存副本）。Web 上传链路的清理行为不变，用户/发行包给的路径一概不碰。
- **用例**：新增 `rejected_install_keeps_the_source_package`（官方包目录与上传暂存两种来路各验证一次：拒装后源包必须还在）。
- **实测**：修复后的二进制上，8 个官方插件装完后 `/www/skiff/official` 仍是 9 个文件；`/tmp/bad-0.1.0.wbpkg` 拒装后原样保留。

### 3. CI 断言同步（1.8.6 那笔提交的收尾）

上一笔改动把 `args.dialog` 收敛成 `args.inLayer`、`formError` 改成带 `ctx`、表单改 `submitMode: "event"`、缺省主题换成「深潜」，但四处断言还钉着旧值，`ci.yml` 的「单测（Linux）」5 例红：

- `budding_boot_create_dialogs_keep_deep_links`：`!args.dialog` → `!args.inLayer`、`if (args.inLayer) closeTopLayer();`、`formError(\n            ctx,`。
- `budding_boot_docker_actions_map_to_resource_endpoints`：`/settings/docker` 的断言从 `settings_page.rs` 改读壳脚本的 `submitJson('/settings/docker'`（表单不再自带 `api.url`）。
- `budding_boot_marks_layer_submits_from_content_slot`：旧机制的禁词列表里 `dialogRegistry` 命中了 `budding-boot.js` 的注释，注释改写为「弹窗注册表」，避免自伤。

## C12 收口：两套文件处理器并存 → 单一路径 `/ui/v1/files/*`

**背景**：`web` 层长期并存两套文件处理器——遗留 `/{p}/files/*`（`handlers/files.rs`，22 路由，1052 行）与 `/ui/v1/files/*`（`handlers/ui/files.rs`）。两者入参解析、错误信封、权限判定、CSRF 各写一套，错误码形状还不同（遗留是数字字符串 `"404"`，新的是语义码 `"not_found"`），前端要写两套解析。budding 壳已全面迁到 `/ui/v1`，遗留路由只剩回收站/配额/上传/下载几个调用点，收口条件成熟。

### 1. 后端：补齐 `/ui/v1/files/*` 并删除遗留

- `handlers/ui/files.rs` 新增 10 个 handler：`upload`（分片）、`download`（流式，目录自动打 zip）、`trash/{list,restore,purge,clear}`、`quotas/{list,set,cancel,scan}`；复用 `files_page::trash_schema` / `quotas_schema`（入参改传 `&body["data"]`）。成功信封统一 `{data: ...}`，错误统一 `fs_api_error` / `ApiError`。
- 删除 `crates/web/src/handlers/files.rs`（22 路由 + `legacy_api_redirect` 308 + `tree`）、`lib.rs` 中 `/{p}/files*` 路由块、`handlers/mod.rs` 的 `mod files;`。`tree` 无前端消费方，直接丢弃不补等价物。
- **形态门禁迁移**：`fs_capability`（`SKIFF_FORM=docker` 受限形态 → 403）原只挂在遗留 `/{p}/files*` 路由组；删组前把它挂到 `/ui/v1/files` 子路由（`files::router(state)` 透传 state），否则受限形态下文件 API 会裸奔。`ui::router()` 签名随之改为接收 `state`。
- `dto.rs` 新增 `TrashRestoreBody` / `TrashIdBody` / `QuotaSetBody`（已有 `FilePathBody` 复用）。
- `ui/files.rs` 顶部定义 `CHUNK_BYTES` 常量，解耦对遗留文件的引用（遗留文件删除后不再有 `handlers::files::CHUNK_BYTES`）。

### 2. 前端：调用点迁移到 `/ui/v1`

- `budding-boot.js`：配额 set/scan/cancel 由 `postPrefixJson(prefix + '/files/quotas/...')` 改 `submitJson('/files/quotas/...')`（解包 `body.data`，前端只看成功/失败，安全）；upload / download 的 `fetch` URL 由 `prefix + '/files/...'` 改 `apiBase + '/files/...'`。
- `files_page.rs` 的 `trash_request` 动作 URL 由 `${prefix}/files/trash/{op}` 改 `${api}/files/trash/{op}`（`api` context = `/ui/v1`，与 `${prefix}` 同一插值上下文）。
- 页面导航 `/{p}/files?path=`、`/{p}/files/view?path=` 保持不变——这是页面路由（SPA fallback 交付壳页），不是 API。

### 3. 行为变更（viewer 页面权限）

- 遗留 `trash_shell` / `quotas_shell` 在**页面 GET** 层对 viewer 做 `authorize(FILE_TRASH_READ/QUOTA_READ)` → 403。删除后页面统一走 SPA fallback（任意已认证用户拿 200 壳页），权限改在 `/ui/v1` 数据端点判定（`guard::action`）。这与主文件页及其它 `/ui/v1` 页面的既有模式一致：viewer 拿 200 壳页 + 403 数据，数据始终受保护。
