## 防火墙：端口参数兼容表单字符串，fail2ban 数值参数同口径

- **改了什么**：`plugins/firewall/src/main.rs` 新增 `u64_param`（数字或去空白后的数字字符串都接受），`port_param` 复用它；`h_rule_add`、`h_port_allow`、`h_rule_remove` 的端口，以及 `fail2ban.jail.ensure` 的 `maxretry / findtime / bantime` 全部改走该入口。补单测 `port_param_accepts_number_and_form_string`。

## 修：Docker 写路径的错误分类（容器生命周期验收时发现）

- **现象**：`POST /ui/v1/containers` 用不存在的镜像 → **503 `dependency.unavailable`**（文案是 Docker 原文 `404 No such image`）；容器重名 → 同样 **503**（文案 `Conflict. The container name … already in use`）。两者都不是「依赖挂了」，503 会让前端当成可重试的临时故障，而正确处置是「改输入」与「换个名字」。
- **原因**：`commands/docker.rs::cmd_err` 只把 `Conflict` 结构化成 409，把 `Unavailable` 一并归进 `BadRequest`；而容器 create / update / action 三个写路径根本没走 `cmd_err`，一律 `DockerCommandError::Unavailable`（→ 503）。两处叠加，正好把「重名」和「镜像不存在」都压成 503。
- **改法**：`cmd_err` 改三分法——`Conflict` → 409、`Unavailable` → 503、其余 Engine 4xx → 400，并接到容器 create / update / action 三个写路径（compose up/down 保持 503：构建/启动失败多属引擎侧，不是输入问题）；`start_container` 对 304 与 `stop_container` 同口径按幂等成功处理（已运行的容器点「启动」不再报错）。单测 `cmd_err_routes_conflict_unavailable_and_bad_request` 覆盖三条分支。
- **复验**：`nginx:alpine`（本地已有）建容器 → 启动（`docker inspect Running=true`）→ 日志 200 → 停止 → 删除（无残留）10 项全过；部署 `d0c8cc4` 后复跑：重名 **409 `domain.conflict`**、镜像不存在 **400 `shape.invalid`**（修复前两者都是 503），12 项全过。
- **连带语义**：`cmd_err` 的 `Unavailable` 分支改判 503 后，镜像/网络/卷六个写命令在「Docker 不可达」时也从 400 变 503（与容器写路径、与 `error.rs` 的错误分类口径一致）；单测 `named_resources_map_unreachable_engine_to_unavailable` 相应改写。CI 首跑（`44310244598`）就是这条断言挡下的，**改动只在 `#[cfg(test)]`，出厂二进制不变**，无需重新出包。

## 修：PHP 扩展安装慢到 30 分钟超时（源按实测吞吐自适应）

- **现象**：新建 `php-8.5`（`php:8.5-fpm-alpine`）在「安装扩展」阶段跑到 30 分钟被判超时；重建（缓存已有 109 MB）仍要 **532 s**，而那一轮只需要装 1 个扩展。
- **取证**：容器内 `apk add` 并未死锁——连续采样 `/proc/<pid>/fd` 见下载字节持续增长。同机同网络测吞吐：镜像默认源 `dl-cdn.alpinelinux.org` **535 KB/s**、清华 **29.5 MB/s**、**阿里 271 KB/s**。该次 `apk add` 拉 67 包 / 338.4 MiB，收尾 purge 26 包。**结论：瓶颈是下载吞吐，不是死锁、也不是编译能力。**
- **关键修正**：最初以为“下载只占三段耗时之一，解包与编译仍是大头”。实测否掉了后半句——同样 338 MiB 工具链，5 MB/s 的源下解包加编译只要几十秒。
- **改法**：`runtime_catalog.rs::installer_prelude()` 在 Alpine 分支里按 `curl -w '%{speed_download}'` 探测 `dl-cdn` / 清华 / 阿里 / 中科大 四个源的 `APKINDEX.tar.gz` 真实吞吐，取最快写 `/etc/apk/repositories`。要点：① **至少快 1.5 倍才换**（小文件测速受首包延迟影响，避免把海外用户从 dl-cdn 误切到国内源）；② 结果缓存到 `/var/cache/apk/.skiff-mirror`（挂宿主，跨容器复用）24 h，首次探测 1.6 s；③ 全候选不可达（纯内网）时不动 repositories、保持镜像默认源，整段 `|| true` 不阻断安装；④ repositories **不带 arch**——apk 会按 `--arch` 自己拼，带上就变成 `.../main/x86_64/x86_64` 全盘失败。
- **验证（测试机，冷缓存：先 `rm -rf /www/runtime/cache/apk/*`）**：`redis`（PECL 编译）**30 s** 成功、`php -m` 已加载；`imagick`（ImageMagick 全家桶）**53 s** 成功、`loaded=yes`；探测选中 ustc **5074 KB/s**，`apk add --simulate --no-cache gcc` 正常解析。对比：默认源冷装 `pdo_mysql` 是 **30 分钟超时**。
- **回归保护**：新增 `installer_prelude_is_shell_syntax_clean`，用 `sh -n` 校验 `format!` 拼出的 shell 并钉住被转义影响的关键片段——这类错误编译期完全看不出来，只会在容器里炸成「apk 装不上」。
- **未做（已记方案）**：Debian 家族（apt 源）未做自适应；进度仍是结算式（执行阶段固定 15%、日志跑完才落库），需 L0 可观测。见 [impl/RUNTIME_PROVISION_SPEED.md](../impl/RUNTIME_PROVISION_SPEED.md)。

### 补：探测判据从 APKINDEX 改为 3 MB range（上线首次生效即发现选错源）

- **现象**：首次部署后冷装 `imagick`，探测选中 **aliyun**，任务卡在「安装扩展」超过 3 分钟（阿里源实际 1.5 KB/s），而 `cache/apk` 只涨到 26 MB。
- **取证（同机同容器，同一时刻四源对比）**：

  | 源 | 3 MB range 真实吞吐 | APKINDEX 估测 |
  | --- | --- | --- |
  | 清华 | **11.0 MB/s** | 1.86 MB/s |
  | 中科大 | 6.6 MB/s | 3.0 MB/s |
  | `dl-cdn` | 301 KB/s | 433 KB/s |
  | 阿里 | **1.5 KB/s**（仅回 215 字节） | **4.2 MB/s（虚高 2800 倍）** |

- **原因**：`APKINDEX.tar.gz` 只有约 500 KB，`%{speed_download}` 被首包延迟与镜像边缘缓存主导，与「下几十 MB 工具链」的真实吞吐无关。
- **改法**：改测 `alpine-virt-<完整版本>-<arch>.iso` 的 3 MB range；响应不足 512 KB 判为「该源无此文件」直接排除（不当成慢）；全部排除则保持镜像默认源。改后同一容器探测 **2.2 s** 选中清华 **9176 KB/s**，`repositories` 格式正确。
- **教训**：源选择这类「看似简单」的启发式，必须用真实大文件校准；小文件测速不仅不准，还会稳定地偏向某一个源（阿里在小文件上表现极好），属于会**自动把用户送到最差路径**的错误。

## 设计：源管理（软件包源 + 容器镜像源），纠正 daemon.json 风险误判

- **新增** [docs/impl/SOURCE_MIRRORS.md](../impl/SOURCE_MIRRORS.md)：三层数据模型（候选清单 / 本机实测 / 生效选择，速度数字只存在于中间层且带时间戳）、apk 与 registry 两套测速口径、应用与回滚、能力面归属、UI 形态。已登记进 `docs/impl.md`，`RUNTIME_PROVISION_SPEED.md` §3 改为指向它（自动探测降级为 `auto` 策略的默认值来源）。
- **纠正误判**：改 `registry-mirrors` **不需要重启 Docker、不重建也不重启任何容器**——它是 dockerd 支持 SIGHUP 热重载的键（`ExecReload = kill -HUP $MAINPID`，测试机 `CanReload=yes`），只有 `data-root` / `storage-driver` / `log-driver` / `iptables` 才需要 restart。现行 `docker_daemon.rs` 恰好按“有运行中容器就不重启”降级，结果是**配置写完不生效**、提示用户去维护窗口手工 restart，属于把热重载当成需要停机的事。
- **registry 测速不能用 `/v2/`**：匿名请求回 401 或空 200，耗时毫秒级，与吞吐无关。须走 manifest → `layers[0].digest` → `Range: bytes=0-3145727` 拉真实 blob，并钉死 digest（tag 会漂移，不同 mirror 命中的层不同，字节数不同就不可比）。
- **未落地**：`mirror` 域（list / probe / apply / rollback）、软件源页 UI、插件形态待定（内核域 + 插件 UI vs 纯插件走 `exec` 粗授权）。

### 实现第一步：daemon.json 改热重载 + registry 测速模块

- **`docker_daemon.rs`：restart → SIGHUP reload**。流程改为「写文件 → `systemctl reload docker` → 轮询 `docker info` 的 mirrors 确认**内存态**已切换 → 提交」。原实现「有运行中容器就不重启」直接导致配置写完不生效，还提示用户自己去维护窗口重启——把一件不需要停机的事说成了需要停机。
  - 新增 `MirrorApplyMode`：`Reloaded`（已生效，容器未动）/ `NeedsRestart`（unit 无 `ExecReload`，如实说明「重启后生效」，不在有容器时替用户重启）/ `Unchanged`。
  - 回滚判据从「docker 是否可用」改成「mirrors 是否真的切换」：reload 可用却没切过去 = dockerd 拒了这份配置，写回原文并再 reload 一次。
  - `mirrors_of` 不绑定 JSON 路径（深度优先找 `mirrors` 数组）：bollard 的 `SystemInfo` 与 `docker info --format` 键名不一致，绑死路径会在版本变化时静默变空，把「未生效」误判成「已生效」。
  - 删掉 `restart_docker` / `docker_ready`；容器数统计降级为「仅用于提示」，读不到就不报数量，不影响变更。
- **新增 `crates/app/src/mirror_probe.rs`**：registry 镜像源测速。先吃 401 挑战换匿名 token，再按 tag 解析 manifest（含 index → amd64 子清单），对首层 blob 发 `Range: 0-3145727` 读满 3 MB，按纯下载时长算吞吐；中途超时按已读字节结算，不足 512 KB 判不可用。结果带 `bytes` / `elapsed_ms` / `bytes_per_sec` / `via_token`，UI 必须显示采样字节数——否则「3 MB / 4 ms」这种缓存命中会被当成带宽。
- **口径实测（测试机，仅验证可行性，不作为速度结论）**：`docker.m.daocloud.io` 与 `docker.1ms.run` 对匿名 manifest 请求**都回 401 + Bearer 挑战**（必须走 token 流程），`dockerproxy.net` 直接放行；`docker.xuanyuan.me`（测试机 `daemon.json` 第三顺位）8 秒无响应。三态（未测 / 失败 / 慢）必须在 UI 上分开。
- **未接入**：`/ui/v1` 测速接口与软件源页 UI（下一批），apk 侧的 `fixed` 选择与 `<runtime>/apk-mirror.conf` 持久化。

## 插件上机前的实测修正（`com.skiff.sources`）

- **`/alpine/last-release` 不存在了**：dl-cdn / 阿里 / 腾讯 / 中科大实测全部 404。据此实现会让「所有源都不可用」。改为读镜像自己发布的 `<base>/latest-stable/releases/<arch>/latest-releases.yaml`，取 `file:` 里 `alpine-virt*-<arch>.iso`；只同步单分支的内网镜像退化为扫 `<base>/` 目录索引取最高 `vX.Y`。

- **prelude 加固定标记**：`# skiff-fixed` 存在则跳过 24 h 过期重测，否则用户的选择会在一天后被自动探测悄悄改掉。归一化处理尾斜杠、`/vX.Y`、`/main|/community` 三种粘贴形态（实测原实现拼出 `.../v3.22//v3.24/main`）。
- **阈值 512 KB → 64 KB**：dl-cdn 从某条线路 8 秒只读到 245 KB（29 KB/s），这是有效的慢，按旧阈值会被说成「不可用」，用户就失去了唯一的线索。错误页量级是几 KB，64 KB 足够区分。
- **补 `bin:/usr/bin/docker` 授权**：`systemctl reload` 的退出码不能证明 dockerd 接受配置（SIGHUP 由 systemd 的 `kill` 发，非法配置也返回 0），必须 `docker info` 读 `RegistryConfig.Mirrors`。缺这条授权时应用一定回滚。
- **测试机实跑 prelude**（5 种缓存形态 + `apk update`）：固定源根 / 带分支 / 完整行 / 内网源 / 自动态全部拼出正确 `repositories`；`apk update` 得到 28677 个包，`apk add --simulate curl` 通过。
- 开发机本地跑通两个探针（`plugin --probe apk|registry <base>`）：ustc 10.4 MB/s、腾讯 2.5 MB/s、dl-cdn 29 KB/s、阿里 ISO 连接被拒；registry 侧 daocloud/1ms/xuanyuan/dockerproxy 四源均可用，其中三个走 token。
