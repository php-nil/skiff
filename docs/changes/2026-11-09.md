## testkit 增加执行期 BusyGuard 探针（`d197041`）

- 动机：`capability.rs::scheduler_call` 在 `is_interop_busy || is_executing` 时返回 403 并记
  `scheduler.deny`，但 testkit 没有「任务执行期再回调 scheduler」的方法，上机无法构造该场景。
- 变更：`plugins/testkit/manifest.toml` 的 `requires` 补 `scheduler`，新增 `scheduler: read` 权限与
  默认停用探针任务 `[[task]] key = "busy-probe" method = "busy_probe" expr = "* * * * *" enabled = false`；
  `plugins/testkit/src/main.rs` 新增 `scheduler_probe` / `busy_probe` RPC（回调 `task.list`，
  被拒时把内核 HTTP 403 文案转成 `RpcError`）。
- 同步：`crates/web/tests/main_flow.rs` 的 manifest 断言更新为 4 项 `requires` 与 busy-probe 任务；
  `docs/PLUGIN_CATALOG.md` 的 testkit 行补 `scheduler` 能力面说明。
- 验证（测试机）：启用 `plugin:com.skiff.testkit:busy-probe` 后「立即执行」，运行历史
  `执行期回调 scheduler 被拒绝：… 内核返回 HTTP 403: 插件正在执行任务，不能再调用 scheduler`；
  审计 `scheduler.deny / deny / 插件正在作为任务执行目标`；验后恢复默认停用。

## 修复：Rust 运行环境站点停止后无法再启动（`9e2c6b1`）

- 现象：`iter-rust-1862702.test`（`site_type=runtime`，绑定 Rust 1.99 环境）停止后点击启动 → 503
  「运行环境 1.99 未运行，请先启动运行环境」，而容器与 `last_status` 均为 running。
- 根因：`set_site_running` 的启动前置检查把「环境必须是 PHP 且 FPM socket 存在」套在所有 runtime 站点上，
  Rust 环境没有 socket，必然被误判。该检查只在启动路径生效，建站直启与运行中站点不受影响。
- 修复：抽出 `ensure_runtime_ready_for_start` —— 所有运行环境只要求 `last_status == running`；
  PHP 额外要求 `socket_path` 存在且文件就绪。错误文案保持可读。
- 回归：`runtime_site_start_guard_only_treats_php_as_socket_based` 覆盖 Rust running/stopped 与
  PHP socket 缺失/就绪四条分支；`cargo fmt` / `clippy -p skiff-app` / `test -p skiff-app`（138 项）全过。
- 发版：force 移动 `v0.1.0` 到 `9e2c6b1`（Release run `42504080508`、CI run `42504074528` 均 success）。
  装机与停止态复验断言见 [TEST_ENV.md](../TEST_ENV.md) §8「`9e2c6b1` 修复轮」。

## 修复：FTP fail2ban 非 21 端口漏封（`2f63aeb`）

- 现象：测试机 FTP 监听 2121，3 次错误密码后 `fail2ban-client status pure-ftpd` 显示
  `Currently banned: 1`，但同一 IP 用正确口令仍能登录。
- 根因：`jail.d/skiff-pureftpd.conf` 只写 `[pure-ftpd] backend/maxretry/findtime/bantime`，
  `port` 从 `jail.conf` 继承 `ftp,ftp-data,ftps,ftps-data`（20/21/989/990）；nft 动作按该端口集生成，
  非 21 端口根本没被拦。fail2ban `reload` 不会重建动作链，必须重启服务。
- 修复：`crates/core/src/kernel/ftp.rs` 抽出 `jail_body(preserve_sshd, listen_port)`，安装/配置时把
  `port = <listen_port>` 写入 jail；`ensure_login_guard` 已在写文件后重启 fail2ban，动作链随新端口重建。
  单测 `jail_body_pins_configured_listen_port` 覆盖 2121/21 与 sshd 保留两条分支。
- 发版：force 移动 `v0.1.0` 到 `2f63aeb`（Release run `42506381545`、CI run `42506375462` 均 success）。
- 复验：第二客户端容器（172.31.0.2）下旧 jail 先复现 `tcp dport {20,21,989,990}`，`config.save` 后
  链变 `tcp dport 2121`；三次错误密码封禁、正确口令被拒、解封恢复的完整断言见
  [TEST_ENV.md](../TEST_ENV.md) §8「`2f63aeb` 三块环境受限项复验」。

## 修复：受限形态「文件管理」入口与直达门禁

- 口径：`SKIFF_FORM=docker`（1Panel 受限形态）能力面只有 docker/identity，内核不提供 fs，
  既不能渲染入口，也不能让直达 URL 借道列出容器内 `/`、`/www`。
- 实现：`crates/web/src/menu.rs` 的管理员判断追加 `state.cfg.form != Form::DockerRestricted`，
  「工具 → 文件管理 / 回收站 / 配额管理」按形态隐藏；`crates/web/src/lib.rs` 把 `/{p}/files*`
  （页面 + 回收站/配额 + 22 个 API）拆成 `files` 路由组并 `route_layer(middleware::fs_capability)`；
  `crates/web/src/handlers/menu.rs` 对 `core/files*` 深链复用同一
  `middleware::check_fs_capability`，统一 403「当前部署形态不提供文件管理能力
  （1Panel 受限形态能力面仅 docker/identity）」。
- 工具分组其余入口（计划任务 `core/tasks`、任务中心 `core/jobs`）不依赖 fs，受限形态保持可见。
- 回归：`crates/web/tests/main_flow.rs::restricted_form_hides_and_rejects_files_management`
  覆盖入口不渲染、页面/深链/API 九条路径 403 且文案可读、容器管理 200；`skiff-web` 单测 52、
  集成 89 全绿。
