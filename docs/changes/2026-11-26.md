## 缺陷一：`gzip_types` 为空时渲出非法主配置，nginx 拒绝加载

**背景**：面板「Web 服务 → 性能参数」只改 `gzip on/off` 时，前端不提交 `gzip_types`；内核把它当空串
直接拼进主配置，渲出 `gzip_types ;`。`nginx -t` 报
`invalid number of arguments in "gzip_types"`，保存被回滚，用户看到 400 `shape.invalid`——
即「只要不清空/重填类型，性能参数就永远存不下去」。

- `crates/app/src/nginx.rs::render_main_nginx_conf`：`gzip_types` 去空白后为空则**整行省略**，
  不再输出只有指令名的空参与行；非空照旧输出。
- 单测 `main_conf_omits_empty_gzip_types_directive`：空值 → 配置里没有 `gzip_types`；非空 → 原样保留。
- 提交 `070ff1d`。上机验证：保存返回「性能参数已保存并通过 nginx -t，随后重载」，主配置只剩 `gzip on;`。

## 缺陷二：回收站「恢复」按钮把壳对象塞进动作数组，整页 `CompileError`

**背景**：回收站行操作要在「恢复失败（目标已存在）」时弹覆盖确认，于是写成
`[{actions:…, onError:…}]` —— 把无 `type` 的壳对象当成数组元素。budding 编译器规则是
`actions` / `then` / `onError` / `elseActions` **必须是带 `type` 的动作数组**，壳对象只能放在处理器
位置本身（上游 `packages/kernel/src/core/compiler/action.ts` 的 `HANDLER_KEYS`）。结果整页编译失败，
页面只剩「页面加载失败」。

- `schema_kit::row_button_chain(text, chain, color)`：行按钮 + 自带动作链，`chain` 直接作为
  `onEvent.click` 的处理器（壳对象形态），成功 `then`、失败 `onError` 各自收尾。
- `files_page::trash_schema` 的「恢复」改用该构件：`actions=[restore(overwrite=false)]`、
  `onError=[confirm → restore(overwrite=true) → 刷新]`、`then=[刷新]`。
- 回归用例（`files_page::tests`）：`assert_typed_action_arrays` 递归断言四个链键的数组元素必须带非空
  `type`；`trash_row_actions_use_typed_actions_and_chain_handlers` 断言恢复按钮仍保留失败分支。
- 提交 `c2a2005`（修复）+ `7810675`（用例指针修正）。用例里把 `trash_schema()` 的裸 page 当成了
  已包 `content` 的结构，CI 上直接 panic —— `trash_schema` 返回 `{type,props,body}`，浏览器报错里的
  `//content/body/...` 是端点再包一层之后才有的路径。
- 上机验证（Playwright，`crates/web/static` 真实壳 + 真实后端）：删除 → 回收站页 0 CompileError →
  点「恢复」→ 条目退出回收站、文件回到原路径；再造「目标已存在」条件点「恢复」→ 弹「恢复失败」
  覆盖确认 → 覆盖恢复成功。

## 缺陷三：PHP 配置保存文案失实 + 真实错误被当成「功能正在适配中」

**背景 A**：保存 PHP 运行参数的落地动作是 `docker restart`（整容器重启），文案却写「重载 FPM」。
实测同环境站点在保存后有 **约 3.2 秒 503**（100 ms 粒度采样 150 次、非 200 共 29 次）。
`crates/docker/src/client.rs::kill_container` 明确「自定义信号不在 MVP 白名单」，所以不改实现、
只把文案改说实：列表/详情提示、按钮、成功消息、作业步骤名与失败文案统一为「重启 PHP 容器」，
页面提示写明「同环境站点在重启期间（约 3 秒）返回 503」。

**背景 B**：壳脚本的 `notReadyPage` 把副标题与告警标题写死成「该功能正在适配中」。端点 4xx/5xx
（例如访问 `/sites/runtimes/none` 这种不存在的实例）也套同一套文案，把「实例不存在」说成「功能没做」，
把排查方向带偏。

- `notReadyPage(title, text, oldHref, oldText, opts)` 支持 `opts.headline` / `opts.subtitle`；
  端点失败分支改为「页面加载失败 / 请检查地址是否正确，或从左侧菜单重新进入」+ 告警
  「数据加载失败 + 真实错误文本」，占位页（未适配功能）行为不变。
- `SHELL_VERSION` 52 → 53（改壳脚本必须升，否则旧缓存继续跑）。
- 提交 `a915b6e`。上机验证：`/sites/runtimes/none` 显示新落地页且正文含「运行环境不存在：none」；
  保存 PHP 配置返回「PHP 配置已保存并重启 PHP 容器生效（同环境站点短暂 503）」。

## 直写闸误判修复 + §5 未验证项 4 闭环（同日续）

**一、`xtask check` 的直写检测把动作声明当成直写**

C11 把动作表 `command` 改成 `admin_fs::write` / `admin_fs::rename` / `admin_fs::copy` 后，CI 的
「契约校验」红在 `✗ actions.rs: 3 处直写，且不在白名单`。原因是 `count_fs_writes` 对
`"fs::write"` 这类 needle 做**纯子串匹配**：模块名尾部的 `fs` 与 `::write` 拼出了 `fs::write`，
三条动作声明被数成三处直写——而它们既没有文件、也没有写入。

- 修法：计数改为按标识符边界，needle 左侧紧邻字符不能是字母数字或 `_`。`std::fs::write`、
  `use std::fs;` 后的 `fs::write(...)` 左侧是 `:` 或行首，仍然计入。
- 负向实测：临时放一个 `crates/app/src/zz_gate_probe.rs`（内容 `std::fs::write`），`check` 仍报
  `✗ zz_gate_probe.rs: 1 处直写`；删掉后恢复通过。`catalog/mod.rs` 白名单基数仍是 2 处，闸门没有放宽。

**二、§5 未验证项 4（孤儿 `.gz` 与二进制体积）闭环**

清理提交 `0b6df70` 删掉的是 `budding-1.8.1-r2` 那一套 6 个文件（含 1.25 MB 的 `budding-1.8.1-r2.min.js`）。
`rust-embed` 按目录嵌入、未开 `compression` 特性，所以**原文件和它的 `.gz` 变体都进二进制**：

- 该批孤儿：raw 2.35 MB + 对应 `.gz` 0.59 MB ≈ **二进制减 2.94 MB**（不是 2.4 MB——按原始字节估会低估）。
- 全量口径：清理前 `static` 共 5.46 MB raw + 1.30 MB gz（≈6.76 MB 进二进制），
  当前 2.45 MB raw + 0.58 MB gz（≈3.03 MB），即 release 二进制比 11-21 前**少约 3.7 MB**。
- 顺带一条观察（不立项）：同一份文本资产在二进制里存两份（原始 + gzip），当前 gzip 变体占静态
  嵌入量的 ~19%。它只服务传输，若将来体积敏感可改为只嵌 `.gz`、运行时按需解压，代价是所有
  请求必须接受 gzip 编码。
