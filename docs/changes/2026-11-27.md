## 四、还原后新一轮上机：站点生命周期误用「重启容器」而非 reload（已修）

**背景**：测试机还原后按「重新发版 → 干净首装 → 装插件/建环境/建站 → 全量测」跑一轮。首轮回归 `round.sh` 106/0、`round_ext2` 20/0、`accept.sh` 50 PASS/0 FAIL/2 SKIP、浏览器 44 路由 44 PASS；`round_ext.sh` 露出 `S06-别名生效` 失败。

**根因**：增删站点别名走 `apply_site_aliases`，它调的是 `restart_nginx()`（**重启容器**），不是注释与契约要求的 reload。实测：加别名后**首个** `curl`（Host 指向别名）直接 `curl: (7) Failed to connect to 127.0.0.1 port 80`；`docker inspect` 的 `StartedAt` 每次都变（`04:32:07Z` → `04:32:13Z`），即整个 nginx（含**其它站点**）在窗口内不可服务。

同类误用还有四处（都属"配置已写好，只需让 master 采纳"）：`create_site`、站点启停 `set_site_running`、默认站切换 `write_default_conf` / `remove_default_conf`、删站 `delete_site`。日志里同一台机器上 vhost 保存路径打的是「nginx 已平滑 reload（worker PID 换代）」，证明 reload 在这套 OpenResty 容器上是可用的——差别只在调用点选错了方法。

**改法**

- 新增 `AppState::activate_nginx()`：取 `nginx_write_lock` → `activate_with`（reload 优先，reload 不生效才回退重启），返回 `Result<(), SiteError>`；调用方不必区分走了哪条。
- 五处"应用配置"改调 `activate_nginx()`；**回滚**路径仍是 `restart_nginx()`（回滚后必须强制把旧配置拉起来，语义相反，不能换）。
- `apply_site_aliases` 的「写 vhost → `nginx -t` → 生效」收进同一把锁（原来 `validate_nginx()` 与 `restart_nginx()` 各取一次锁，中间可被别的写入插队）。
- `create_site` 补 `nginx -t`：原来是「写完直接重启」，坏 vhost 只能靠容器起不来兜底；现在与 `set_site_policy` / `apply_tls` 一致（写 → 校验 → 生效）。
- 副作用（有意）：nginx 容器**未运行**时建站从"顺手把容器拉起来"变成"报『nginx 运行环境未启动，无法校验配置』"——与 `set_site_policy` / `apply_tls` 早已如此的口径对齐。

**未改**：nginx **主配置**保存（`crates/app/src/nginx.rs`）仍走重启。它带 300 ms 起的启动核对与回滚链，且 `worker_processes` / `worker_rlimit_nofile` 这类指令 reload 语义与重启不同，本轮不动；要改需单独一轮验主配置各指令。

**验证（上机，包 `3fbf8e2` / 12,552,580 B / `baac26fb…`）**

- 容器不再重启：连续加/删别名、建站、默认站双向切换、删站，`docker inspect -f '{{.State.StartedAt}}' skiff-web-nginx` 全程不变；日志改打「nginx 已平滑 reload（worker PID 换代）」。
- **reload 的生效是异步收敛，不是"接口返回即生效"**：实测加完别名后首个请求仍 404、停站后首个请求仍 200，`0.2–0.5 s` 后变成预期值（采样 `1:200 2:404 3:404…`）。旧 worker 在 SIGQUIT 后要排空连接，期间仍可能接新连接按旧配置应答。修前是"连接被拒（`Failed to connect`）+ 全站受影响"，修后是"单站亚秒内返回旧结果"——后者不打断在途请求，也符合 nginx reload 语义，因此**用例判据改为「2 秒内收敛」**（`round_ext.sh` 的 `S13` / `S06` 已按此改），不再断言"首个请求即 200"。
- 回归：`round.sh` 106/0、`round_ext.sh` 32/0、`round_ext2.sh` 20/0、`accept.sh` 34/0/3 + B 组 15/0/1、浏览器 44 路由 44 PASS。

## 七、C15 catalog/mod.rs 流式下载的正文落盘与发布替换：白名单彻底清空

**背景**：`KERNEL_ARCH_AUDIT.md` §3「未闭环问题」的唯一残留——xtask `check-channel` 白名单登记 `catalog/mod.rs` 共 2 处（`fs::write` + `fs::rename`）。原审计稿的"不做原因"是：通道单次写上限 256 KiB（`MAX_REQUEST_BYTES`）且无流式接口；发布必须一次性 rename（通道改名对已存在目标是先删后移）。

**根因重新审视**

原审计稿有一个过时假设：`MAX_REQUEST_BYTES`（256 KiB）是 UDS 跨进程分帧的限制，**AdminFs 是进程内直调 `Fs`（不走 HTTP/UDS）**，所以这个 256 KiB 限制对内核通道来说是保守过头的默认值。进程内调用不走分帧，`max_request_bytes` 字段存在但只是配置校验，实际 IO 不受限。

`MAX_FILE_BYTES = 4 GiB` 才是单文件的自然上限（也是 `FsConfig` 已有的字段）。把 AdminFs 的 `max_request_bytes` 调上去，不会破坏任何安全边界——内核通道本来就是"管理员进程内直接调"，没有跨进程传输的帧限制。

**替换方案**

原来 store_blob 的三连：
```rust
fs::write(part, &reply.body)?;   // 整块落临时文件
set_private(part)?;               // 0o600
fs::rename(part, dest)?;          // 发布（POSIX 原子替换）
```

改成：
```rust
self.admin_fs.write_kernel_mode(dest, &reply.body, 0o600)?;
```

这一行等价于原来的三连：
- `WriteMode::Replace` = Fs::write 内部先写 tempfile 再 POSIX rename（原子替换，和原 `fs::rename` 一样）
- `write_kernel_mode` = 先 Replace 写 + 再 chmod 0o600
- 权限位从 `set_private` 合并进 `write_kernel_mode` 的 mode 参数
- 写路径 + 发布 + 权限设定都走 Fs 通道，落审计

**改动清单**

| 文件 | 改动 |
| --- | --- |
| `crates/app/src/admin_fs.rs` | `with_protected` 的 `FsConfig` 显式覆盖 `max_request_bytes: MAX_FILE_BYTES as usize`（4 GiB） |

**等价性论证**

| 原方案 | 新方案 | 等价点 |
| --- | --- | --- |
| `fs::write(part, body)` | `write_kernel_mode(dest, body, 0o600)` | body 都是完整内容（已从 transport 拿到内存）；Fs::write 内部是 tempfile + POSIX rename（原子），等价于原 `fs::rename(.part, dest)`；权限位 0o600 一致 |

| `set_private(part)` | （已包含在 write_kernel_mode 第三个参数里） | 0o600 权限位 |
| 无审计 | 每次 write 走 Fs 通道 | 落审计（path / bytes / mode 都记录） |

**架构意义**

- §3「未闭环问题」从"白名单只剩两处"变成"白名单零处"——**通道唯一原则在 app/core 全覆盖**
- AdminFs 的 `max_request_bytes: 4 GiB` 不是放宽安全边界，是让配置值与实际调用路径（进程内直调而非 UDS）对齐；HTTP handler 的上传走 upload_chunk，仍受 UDS 帧限制的 `MAX_REQUEST_BYTES`
