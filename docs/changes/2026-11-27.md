## 一、C6 `store/db.rs` 拆文件（落地）

**背景**：条目为搁置项，三条重启条件（schema 变更批次 / 两会话同改 / ≥1765 行）按 HEAD 实测**均未触发**；按原口径不该动，本轮直接执行，故一并把 C6 从 §4 删除——不留「已拆完仍挂搁置」的悬空条目。

**拆分前实测**（HEAD `7a909b7`，1177 行）：连接车道 209 行 + `SCHEMA_V*` 常量 616 行（52%）+ 用例 350 行（10 个）。表级读写早在 `db/` 16 个子模块，`backup_to` 与审计裁剪在 `db/maintenance.rs` 的长操作车道——条目原文「迁移、查询与事务集中一个文件」与 §1 表「连接+迁移+备份同文件」都失实，本轮按事实纠正。

**新结构**

| 文件 | 行数 | 内容 |
| --- | --- | --- |
| `db.rs` | 139 | 连接、锁车道、`CURRENT_SCHEMA_VERSION`、`mod` 声明 |
| `db/migrations.rs` | 94 | 台阶表 + 单步事务（`apply` / `step`） |
| `db/migrations/schema.rs` | 621 | `SCHEMA_V1..V22` DDL 正文 |

| `db/tests.rs` | 102 | 4 个 `Db` 面用例（备份 ×2、回收站、配额往返） |

- `Db` 对外 API 未变。私有方法 `Db::migrate` / `Db::migrate_step` 改为 `migrations::apply` / `step`；`open` / `open_in_memory` 里迁移现在发生在装配 `Db` 之前（原先是先建 `Db` 再取锁迁移）。行为等价：那一刻还没有其他持有者，`configure` 与迁移用的是同一个连接。
- 台阶表不再写死数组长度 `22`，条目数即长度，新增版本只加一行。
- `db/maintenance.rs` 的 `super::StoreError` 改为 `crate::StoreError`：db.rs 不再导入该类型，`super::` 路径失效。

**验证（纯移动）**

- 10 个用例名一一对应；逐用例正文比对：8 个逐字一致，2 个只差改名的调用点（`db.migrate()`→`apply(&db.conn())`、`Db::migrate_step(`→`step(`）；三处 `for batch in [...]` 常量数组被 rustfmt 重排换行，条目与顺序不变。
