## 方向修正：否决 `host_action` 模板方案，改为 `exec` 能力面（粗授权 + 全审计）并落地内核底层

- **为什么改**：同日成文的方案 A（manifest `[[host_action]]` 命令模板）判为**繁琐且不达目标**——模板结构 + 槽类型系统 + 渲染器 + 逐条确认页 + 4000 行迁移，表面积是目标的三倍；二进制白名单与槽类型表仍是内核侧封闭集合（加 `nginx`、加一个值类型照样发内核版），「零内核改动」不成立；firewall/ftp 各有契约与测试、改动频率低，搬家无用户价值。**根本理由**：类型系统防的是「命令跑坏」（可靠性），不是「提权」（安全），而安全不变量只有几条且与领域无关。
- **新模型**：照 `fs` 现成的「粗授权 + 全审计」做，不造第二套——权限串 `exec:run` + 对象授权 `bin:<绝对路径>`（与 `path:` 同形态、同一套安装期确认与落库），插件自己决定跑什么，内核只校验二进制身份（授权命中 / 文件本体 root 属主且不可被非 root 写 / 不在内核数据根内 / 非包装器）后原样执行 argv 并逐次审计 argv 全文。**明示粒度**：授权 `apt-get` 即等价授权 root。
- **代码（内核底层）**：`crates/wire` 加 `CAP_EXEC_RUN`；新建 `crates/model/src/exec.rs`（`bin:` 前缀、包装器名单、`bin_risk` 三档，7 例）与 `crates/plugin/src/execgrant.rs`（三道闸判定 + `ExecError`，8 例）；新建 `crates/core/src/kernel/exec.rs`（handler：解析/权限/判定/执行/审计/截断，6 例）并挂上 `routes.rs`；`host_run.rs` 的 `HostOutput` 补 `code`；`pkgfmt` 加 `Capability::Exec` 与 `bin:` 资源校验（拒绝目录与包装器，与运行期共用 `skiff_model::exec` 名单）；`sdk` 加 `host_exec` / `host_exec_with_stdin` / `host_exec_full` / `bin_grants`。

## `exec` 改为「提交作业」：命令执行进运行记录，与环境安装同构

- **为什么改**：同步等结果的协议把命令的耗时变成内核的 HTTP 超时——`apt-get install` 几分钟，插件只能盲重试；而只记「谁请求了什么」的审计，复查时看不到过程。**记录分流**定为本条口径：**文件读写进审计**（`audit`，90 天，安全追溯），**任务执行进运行记录**（`jobs` + `job_logs`，过程输出 / 退出码 / 取消）。环境安装、镜像拉取、站点创建本来就在这套作业上，命令执行接进来后二者同构：同一张表、同一套状态机与 SSE 详情页、同一套取消。
- **协议**：`exec/run` 改为提交作业（返回 `job_id`，可按 `wait_sec` 前台短等，默认纯异步）；新增 `exec/status`（状态 + 结果 + 增量日志，`after` 游标）与 `exec/cancel`（协作式，250ms tick 命中即 `systemctl stop` 单元）。请求进来先跑完三道判定再建作业，失败不落僵尸作业；`stdin` 不进作业参数、不落库，只在进程内 map 交给执行体一次。
- **代码**：`host_run.rs` 新增 `run_host_stream`（逐行回调 + 取消检查 + 单元清理），`run_host` 改为其薄封装，ftp/firewall 行为不变；`kernel/exec.rs` 重写为「提交/查询/取消 + 作业执行体」，失败按 `exit` / `timeout` / `channel` / `cancelled` 分类结算；`wire` 加 `CAP_EXEC_STATUS` / `CAP_EXEC_CANCEL`；`app/jobs.rs` 加 `KIND_HOST_EXEC` 与 `finish_err_result`（非零退出仍保留 stdout/stderr）；`sdk` 加 `host_exec_submit` / `host_exec_status` / `host_exec_cancel`，`host_exec_full` 改为「提交 + 轮询到终态」并保持旧返回形状；`web/handlers/jobs.rs` 识别 `host.exec`（类型/目标文案，隐藏重试——重放特权命令必须重新走插件授权）。
- **上限调整**：`timeout_sec` 默认 600（原 120）、上限 3600（原 600）——作业化后不受 HTTP 生命周期约束；新增 `wait_sec ≤ 120`、单作业过程日志 ≤ 2000 行、同一插件并发命令 = 1（409）。

- **验证**：`cargo fmt --all --check` 通过；`clippy -D warnings`（core/app/web/sdk/wire）通过；测试：`skiff --bins` 56（其中 exec 8）、`skiff-app` 349、`skiff-wire` 10。**未上机验收**：`run_host_stream` 的 systemd 真实执行、取消与超时清理只在 Linux 跑得到。

## 执行通道抽为 `skiff-host`：授权与通道正交，内核自身动作不再各写一遍

- **为什么改**：上一条把「环境安装复用 `exec`」写成了「共用记录与生命周期」，漏了真正要统一的那一层——**执行通道**。环境安装是内核自己发起的，确实不需要 `bin:` 授权，但它执行的宿主命令（重启服务、装包、生成证书、探测地址）不该在 `app` 里再写一遍 `Command::new` + 超时 + 收尾。授权与通道是两个正交的东西：插件走 `exec` 面（先授权再进通道），内核自己直接进通道。**混在一起的代价就是每个调用点复制一份执行逻辑。**
- **新 crate**：`crates/host`（`skiff-host`，workspace 16 → 17）。从 `crates/core/src/kernel/host_run.rs` 提升为公开 API：`HostSpec` / `HostOutput` / `HostRunError` / `run` / `run_stream`。两种模式共用同一套「逐行读 / 250ms 取消检查 / 超时后清理」：`HostSpec::privileged`（`systemd-run` 瞬态单元，root，脱离主服务沙箱）与 `HostSpec::direct`（直起子进程，用于 `openssl`、`ip` 这类不要 root 的命令）。清理按模式分流：特权停单元、普通杀子进程。
- **代码**：`crates/core/src/kernel/host_run.rs` 删除，`ftp` / `firewall` / `exec` 三个能力面改用 `skiff_host`（`exec` 那层多余的包装函数一并删掉）；新增 `crates/app/src/host.rs`——`AppState::run_host_in_job`（过程行写 `job_logs`、取消接 `cancel_requested`、错误翻中文、2000 行上限）与 `run_host` / `run_host_msg`（作业外探测，返回 `HostRunError` 以便调用方区分「超时=结果未知」与「起不来」）。
- **收口的调用点**：`docker_daemon`（`systemctl restart docker`，特权；超时文案仍保留「结果未知，Docker 可能仍在重启」）；`sites/network`（`ip -4 -o addr show`，原来在阻塞池裸跑无超时，现在 8 秒上限）；`sites/crud`（`openssl req` 自签生成，30 秒上限，去掉 `spawn_blocking`）。**`docker_daemon` 有一处语义变化**：原来在主服务进程里直接 spawn `systemctl`（继承主服务沙箱），现在与其他特权动作一致，跑在瞬态单元里；代价是依赖 systemd 可用——本项目的前提（`host_run` 一直是 ftp/firewall 的立足点），收益是不再受主服务沙箱限制。
- **明确留下的例外**：`crates/app/src/sites.rs` 的 `openssl` 文本解析与证书配对校验仍用同步 `std::process`——它是页面渲染路径的纯解析（已有缓存、无取消与超时语义），不管理执行过程；硬改 async 会把渲染链一起污染。这条边界写进了设计文档而不是留在代码里当隐性约定。
- **文档**：`HOST_EXEC_DESIGN.md` 新增「谁授权、谁执行、谁记录」四层表（协议 / 授权 / 通道 / 记录）与两种执行模式对照，§2.4 把「不经过 exec 的 bin: 授权」修正为「不经过 `exec` 协议，但必须经过同一条通道」，§4 / §6.1 / §7 同步；`KERNEL_EXEC_CONTRACT.md` 头部与测试矩阵改指 `crates/host`；`03-architecture.md` 分层图加执行通道一行；`AGENTS.md` 与决策 #11 的 crate 计数改 17。

## 通道无例外：`exec` 与 `fs` 成为唯一入口，记录代替权限设计

- **原则（用户拍板）**：`exec` 与 `fs` 是内核的两个底层能力，**所有操作都必须经过它们，不能有例外**。行为一律留记录（执行进运行记录、文件写进审计），这样就不必为每个功能逐条设计权限——查得到，就不必预先声明到每条命令每个路径。
- **消掉的最后一处 exec 例外**：`crates/app/src/sites.rs` 的 `openssl`（证书文本解析、配对校验）改用 `skiff_host`（`direct` 模式，10s 上限）。为走通道，`parse_cert_text` / `cached_cert_text` / `verify_cert_pair` / `site_tls_info` 改为 async，两个 web 调用点去掉 `blocking_fs` 包装，`upload_cert` 只把纯写盘留在阻塞池。现在 `crates/app` 与 `crates/core` 的非测试代码里 `Command::new` 为 **0**。
- **fs 侧建立内核自身主体**：`AdminFs::write_kernel` / `remove_kernel`（`crates/app/src/admin_fs.rs`）——复用同一个 `Fs` 实例（同一套临时文件 + rename、同一份路径代数、同一张 `audit` 表），主体固定 `Principal::admin("system").with_protected_write(true)`，`remove` 一律 `permanent`（系统配置不进回收站）。首个迁移点：`/etc/docker/daemon.json` 的写入与取消还原（`docker_daemon.rs`），守卫改为持有 `Arc<AdminFs>`。
- **「有记录」有了断言**：新增用例 `kernel_write_leaves_audit_trace` —— 内核写一次 `daemon.json`，审计表里必须出现 `action=fs.write` / `actor=system` / `result=ok` / `target` 指向该文件。契约 §2.1 由「两类主体」改为**三类**，补 `system` 行与「内核自身也是主体，不是例外」一节。

## 计划任务也进 `exec`：内置任务的命令动作改为 `host.exec` 作业

- **为什么改**：站点备份原来用 `tar` crate 在进程内打包，是内核自己做的文件 IO——没有作业、没有过程日志，超时只能「放弃等待、进程继续跑」。这与同日定下的「`exec` / `fs` 是唯一入口，所有操作都要经过、都有记录」冲突：计划任务是内核的动作，不是例外。
- **判据**：**有外部命令**的内置任务走 `exec`（`site-backup` → `tar`）；**没有命令可跑**的留在原语自身——`db-vacuum`（SQLite `backup_to`）、`audit-prune`（SQL 删除）是库内事务，`trash-prune` 走 `AdminFs`（`fs.remove` 已有审计）。判据是「这件事有没有可执行文件」，不是「任务是不是内置的」。
- **代码**：执行体 `run_exec_job` / `handle_channel_failure` / `truncate` 从 `crates/core/src/kernel/exec.rs` 迁到 `crates/app/src/host.rs`（`drive_exec_job` / `clip_text`），插件 `exec` 路由与计划任务共用一份；新增 `KernelExec::run(&Db, &JobService)`（提交 + 审计 + 执行 + 读回终态）与 `AppState::exec_kernel`；`TaskService` 持有 `Arc<JobService>`（`AppState.jobs` 同步改 `Arc`，不再各 new 一份）；`AdminFs::ensure_dir_kernel` 补内核建目录原语（逐级建、每级留 `fs.mkdir` 审计）；`crates/app` 去掉 `tar` 依赖。
- **作业口径**：`target_type=host`、`target_id=<任务 id>`（同任务串行、跨任务不阻塞）、`created_by=system`、`params.origin="sched"`；审计 `actor=system` / `source=sched` / `action=exec.run`，detail 带 `bin`/`risk`/`job`/`argv`/`timeout`/`origin`/`target`。
- **语义变化**：任务 `timeout_secs` 现在是作业与通道的超时——超时即 `systemctl stop` 瞬态单元，不再只是「内核不等了」；站点备份默认上限 30s → 600s（`SITE_BACKUP_TIMEOUT_SECS`）。
- **闸门**：`xtask check` 内核文件写基线 141 → 140（`File::create` 不再由内核做）。
- **文档**：`KERNEL_EXEC_CONTRACT.md` 补 §4.1「内核自有作业」与审计/测试矩阵；`KERNEL_SCHEDULER_IMPL_NOTES.md` 补 §8.7；`sections/03-architecture.md` §3.1 新增「内核能力与记录（唯一路径）」图，§3.3 表补 `exec` / `scheduler` 两行。
- **验证**：`fmt --check`、`clippy -D warnings`（app/core/web）通过；`xtask check` 全绿（通道 0 处直呼、文件写 140/140）；测试 `skiff-app` 353、`skiff-web` 87 + 203、`skiff --bins` 53、`skiff-host` 6。**未上机验收**：`tar` 真实打包与单元清理只在 Linux 跑得到，开发机覆盖「作业成对出现 / 缺 `tar` 提交前即拒」两条分支。

## 首轮 CI 红：三处用例把 root 特权当成测试前提（已修）

- **现象**：`单测（Linux）` 报 3 例失败——`execgrant` 的 `granted_binary_*` 与 `directory_grant_*`（断言 `NotGranted` / `Ok`，实际得到 `NotTrusted("属主不是 root")`）、`site_backup_runs_through_an_exec_job`（`tar` 作业退出码 1）。
- **根因**：都不是代码缺陷，而是用例把环境当常量。`bin:` 的信任闸要求二进制属主是 root，CI runner 造不出来；站点备份要真跑特权通道，而 runner 上没有可用的 systemd（`systemd-run` 以退出码 1 拒绝）。Windows 开发机靠 `cfg(not(unix))` 的空实现把这两点掩盖了。
- **改法**：`execgrant::resolve` 拆成 `resolve_candidate`（形式/存在/本体/包装器/数据根）、`check_owner`（信任闸）、`authorize`（授权命中）三步——授权命中与整条判定各自断言，整条判定按实际属主分流，**不放宽信任闸**。站点备份用例改为断言「记录与产物一致」：成功必须有归档且 `result.success`，失败必须带错误类并已结算。
- **教训**：平台相关的用例要么把环境判据写进断言分流，要么就别断言那一步；`cfg(target_os)` 不足以描述「有没有 systemd、跑在不在 root 下」。

## `accept.sh` B 组与登录实现脱节：按 budding 原生链路重写（真机发现并修正）

- **现象**：本轮全新安装（`280345e` 资产）后跑 `sh accept.sh --group b`，`B1a 登录页含 csrf 隐藏域` 判 FAIL（「没抓到 csrf」），整组中断，B 组 12 条全部跑不到。
- **根因**：登录页早已改为 budding 原生页——`GET /{p}/login` 只返回壳 + `budding-login.js`，CSRF 由 `GET /ui/v1/auth/login` 下发，页面里根本没有 SSR 表单的 `<input name="csrf">`。脚本仍按旧表单调 `/{p}/login` 取隐藏域、用 `303` 判登录成功、用 `/{p}/password` 改密。属**测试资产与实现脱节**，不是产品缺陷。
- **手工复核（判定非产品问题）**：`GET /ui/v1/auth/login` 200 并返回 119 字符 `csrf_token`；错误口令 401 `auth.unauthenticated`「用户名或口令不正确」；正确口令 200 + `redirect_to=/cb5mgdk7`；`GET /ui/v1/session` 200。
- **改法**（`deploy/accept.sh` B 组，断言编号语义保持不变）：
  - `B1a`：改为 `GET /ui/v1/auth/login` 200 且响应含 `csrf_token`；
  - 新增 `B2b`/`B2b1`：错误口令 401 + 文案断言（负例放在成功登录**之前**，随后的成功登录会把限流计数清零，不污染 B4）；
  - `B2`：由「表单 POST → 303」改为「JSON POST → 200」，`B2a` 改读 JSON 的 `redirect_to`；
  - `B5`：CSRF 负例改 `POST /ui/v1/settings/password` + `x-csrf-token: bogus`，仍断 403；
  - `B3a`：改 `GET /ui/v1/settings` 200；`csrf2` 改从 `GET /ui/v1/session` 取；`B3c` 改密断 200；
  - `B4`：限流循环改 JSON 提交（原「整页保留避免截断切在标签中间」的注释按新形态改写）。
- **验证**：测试机 `sh accept.sh --group b` → **PASS 13 / FAIL 0 / SKIP 1**（B4 未开 `--with-rate-limit`，属设计性 SKIP）；`sh -n deploy/accept.sh` 本机通过。
- **教训**：验收脚本断言的是**实现形态**（表单隐藏域、303），实现一改口径就失效且以 FAIL 呈现，容易被误判为产品回归。断言应尽量贴在稳定的契约面（端点 + 状态码 + 文案），并在前端形态迁移时同步脚本。
