### 结论（四维评级）

模块划分 **A−**、职责边界 **B**、依赖关系 **A−**、复用性 **B−**。

分层骨架已稳：`docker` 收敛为纯 I/O（978 行）、`core` 回到装配层（`kernel/` 拆 7 文件、最大 235 行）、
`core → web` 反向依赖消失、`store` 按聚合拆分保持、`policy`/`compose`/`wire`/`model` 的隔离仍成立。

**剩余缺陷同源：业务动作没有归口。** 「授权 → 执行 → 留痕」这套动作在 Web、JSON API、CLI、
插件 UDS 四条路径上各拼一遍，于是同一动作的副作用与审计条数各不相同。

### 已致缺陷（4 条）

1. **装/卸包各写两条审计**：`plugin/install.rs:252,343` 写 actor=`system`，
   `web/handlers/plugins.rs:356,436` 与 `core/commands.rs:168` 又各写一条。现有测试用 `.any(...)`
   断言「存在一条」，结构上抓不到重复。第五轮「CLI 装包补审计」补的是重复，不是归属。
2. **11/13 个判权点不留越权痕迹**：只有 `containers::action` 与 `kernel::docker_call` 写 deny 审计；
   `resources.rs` 6 处、`api.rs` 2 处、`containers::detail`/`logs_sse` 全不写。按 `result=deny`
   筛不出镜像删除、网络创建、API 重启的拒绝尝试。
3. **CLI `plugin enable/disable` 副作用缺失**：`core/commands.rs:201-210` 不停进程、不写审计，
   Web 侧两者都做。运行中停用 = 进程仍在跑 + 无留痕 + UI 显示已停用。
4. **插件 UI 静态文件无认证**：`web/lib.rs:186` 路由未挂认证提取器，`middleware.rs:34-38` 的
   `is_exempt` 又把它从入口前缀检查里豁免 → 不登录、不知前缀即可 `GET /plugins/<id>/ui/<file>`，
   靠 200/404 枚举已安装插件。JSON 侧 `/api/v1/plugins/ui` 要 `AuthUser`，两侧口径不一致。
